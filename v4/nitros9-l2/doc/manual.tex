\chapter*{About This Manual}
\addcontentsline{toc}{chapter}{About This Manual}
\renewcommand{\thesectname}{About This Manual}

This manual describes the software that turns a TFR/911H into a small,
complete OS-9 system: NitrOS-9 Level 2, booted by the board's firmware,
with a disk, a clock, a Unix-flavored set of commands, an editor, a sound
chip, games, and a network connection through a FujiNet. It also describes the hardware that the firmware
emulates for OS-9, and how to rebuild everything.

\section*{Audience}
This manual is for anyone with a TFR/911H on their desk: people who know
some Unix and want to find their way around OS-9, CoCo veterans who want
to know what is different about this machine, and people who want to
change the firmware or the disk. No knowledge of OS-9 is assumed in
Chapter~1.

\mainmatter
\chapter{Introduction}
\chapterpages
\renewcommand{\thesectname}{Introduction}

This chapter introduces the TFR/911H, the two levels of OS-9, the two
OS-9 systems the board runs, and what was added to NitrOS-9 Level 2 for
it. It ends with a first session at the keyboard.

\section{The TFR/911H}

The TFR/911H is a single board computer built around a genuine Hitachi
HD6309 microprocessor---the CMOS cousin of Motorola's 6809, with extra
registers and a faster native mode---and a Raspberry Pi RP2350B
microcontroller. Everything that is not the CPU is done by the RP2350B:
\begin{itemize}\setlength{\itemsep}{0pt}
\item It makes the 6309's E and Q clocks, one bus cycle at a time.
\item It is the memory: 256K of the RP2350B's 520K of SRAM, behind an
emulated MMU.
\item It is every I/O device: a serial port for the console, a hard disk,
a clock, interrupt timers, a sound chip.
\end{itemize}
One of the RP2350B's two cores runs the 6309's bus; the other talks USB
to a program on your computer, the \emph{tether}, which is the board's
terminal, its disk drive, and its clock. The 6309 runs at about 2.8 to
3.2~MHz---faster than the 1.79~MHz of the fastest Color Computer.

The TFR/9 family of boards was designed to make very cheap 6809-family
computers that run OS-9. Its design files and software are at
\file{github.com/strickyak/tfr9}.

\section{OS-9 Level 1 and Level 2}

OS-9 was written by Microware Systems Corporation in 1979 and 1980 for
the Motorola 6809. It is a real-time, multitasking, multi-user operating
system that will look familiar to anyone who knows Unix: a hierarchical
file system, a shell with pipes and redirection, devices that are files,
processes with parents and children. It was written to be small and to
run from ROM, so everything in OS-9 is a \emph{module}: a
position-independent, re-entrant block of code or data with a header and
a CRC, which the system can find in memory by name. The kernel, the
device drivers, and the commands you run are all modules.

The 6809 can address only 64K of memory, and OS-9 comes in two
\emph{levels} that differ in what they do about that.

\begin{description}\setlength{\itemsep}{0.5ex}
\item[\sans{Level 1}] runs everything in a single 64K address space: the
kernel, every process, every module. It needs no memory management
hardware, which made it right for the first Color Computers. Tandy sold
OS-9 Level One for the Color Computer in 1983.

\item[\sans{Level 2}] uses a memory management unit to give each process
its own 64K address space, made of 8K blocks drawn from a larger physical
memory---up to 2M. The kernel lives in a space of its own. Processes cannot
see or damage each other's memory, and many more can run at once. Tandy
sold OS-9 Level Two for the Color Computer~3, whose GIME chip has the
MMU, in 1987.
\end{description}

NitrOS-9 began in the 1990s as a rewrite of OS-9 that made use of the
Hitachi 6309's extra registers and instructions. Today the NitrOS-9
Project maintains it as open source, for both the 6309 and the 6809, for
Level 1 and Level 2, and for many machines besides the Color Computer.

\section{Level 1 on the TFR/911H: TurbOS}

When the TFR/911H firmware starts, it waits at its console prompt,
\texttt{TCL>}, a small Tcl interpreter (see \rp{tcl}{8}). Typing
\type{bye} there starts \emph{TurbOS}, a small OS-9 Level 1 system that
the firmware loads into the 6309's memory as a single 64K image, from its
own flash.

TurbOS runs without a disk. Its kernel, I/O manager, SCF terminal manager,
terminal driver, Shell, and a handful of commands (\cmd{mdir}, \cmd{mfree},
\cmd{procs}, \cmd{sleep}) are modules in the image. Its prompt is
\texttt{TOS:}:
\begin{ex}
TOS:\textbf{mdir}
 Module directory at 00:00:59
kernel  init  tk  ioman  scf  scvt  term  go  shell  mfree  mdir  procs  sleep
\end{ex}
TurbOS comes from the TFR/9 project's TurboLab work, in the
\file{v4/turbolab} directory of the TFR/9 source. The rest of this manual is about Level 2.

\section{Level 2 on the TFR/911H: NitrOS-9 V3.3.0}

Typing \type{l2} at the \texttt{TCL>} prompt starts NitrOS-9/6809 Level 2
V3.3.0, built for the Color Computer~3. The firmware copies a small
launcher and the kernel's boot track into memory and resets the 6309,
which boots in about half a second:
\begin{ex}
NitrOS-9/6809 Level 2 V3.3.0
Tandy Color Computer 3
(C) 2014 The NitrOS-9 Project
Fri Oct 16 17:23:34 2026
http://www.nitros9.org

NitrOS-9 Level 2 on the TFR/911H.  Unix-style commands: man unix

Shell

OS9:
\end{ex}

\subsection{The disk}

The disk is a file on your computer, \file{v4/nitros9-l2/level2.dsk}: an
RBF disk of 99,999 sectors (24.4M) that the tether serves to EmuDsk a
sector at a time. It holds \file{OS9Boot}, the rest of the operating
system, which the kernel loads at boot; the commands in \file{/DD/CMDS};
the system files \file{errmsg} and \file{helpmsg} in \file{/DD/SYS}; and
story files for \rp{zm}{6} in \file{/DD/GAMES}. Whatever you save goes to
the file at once.

With a FujiNet attached, typing \type{l2fn} instead of \type{l2} boots from
the FujiNet's first device slot, a copy of this disk on its SD card or a
TNFS server; \file{/DD} is then the DriveWire disk \file{/X0}, and the
tether's disk is \file{/H0}. See \rp{fujinet}{4}.

\section{A First Session}

Plug the TFR/911H into a USB port and, in the \file{v4} directory of the
TFR/9 source, run \file{run-l2.sh}. It starts the tether, which boots
NitrOS-9 by typing \type{l2} for you (or reconnects, if NitrOS-9 is
already running):
\begin{ex}
$ \textbf{WIRE=/dev/cu.usbmodem31201 sh run-l2.sh}
TFR/911H on /dev/cu.usbmodem31201, disk .../nitros9-l2/level2.dsk.
^C goes to OS-9; quit with ^] .
\end{ex}
Then look around. \cmd{man unix} lists the Unix-style names; \cmd{ls -l}
lists a directory; \cmd{info} shows the whole system:
\begin{ex}
OS9:\textbf{ls -l /dd/cmds}
OS9:\textbf{cd /dd}
OS9:\textbf{pwd}
/DD
OS9:\textbf{info}
\end{ex}
Write a file with \cmd{vi}, and look at it with \cmd{cat}:
\begin{ex}
OS9:\textbf{vi notes}
OS9:\textbf{cat notes}
\end{ex}
Play something:
\begin{ex}
OS9:\textbf{zm zork1}
OS9:\textbf{tetris}
\end{ex}
The shell is \cmd{tsh}: the arrow keys move about in the line you are
typing and bring back the lines you typed before, and \key{Tab} finishes
the name of a command or a file. \rp{tsh}{1} has the rest.

\key{Ctrl/C} interrupts the program that is running, as on Unix. To leave
the tether, press \key{Ctrl/]}; NitrOS-9 keeps running on the board, and
\file{run-l2.sh} will reconnect to it.

OS-9 differs from Unix in a few ways you will meet early:
\begin{itemize}\setlength{\itemsep}{0pt}
\item Each process has two current directories: the \emph{data}
directory, for files (\cmd{cd}, \cmd{pwd}), and the \emph{execution}
directory, where commands are found (\cmd{chx}, \cmd{pxd}). Both start
at \file{/DD} and \file{/DD/CMDS}.
\item The pipe symbol is \texttt{!}, not \texttt{|}. \texttt{>>} redirects
standard error; there is no append. \texttt{\&} runs a command in the
background, as on Unix.
\item File names are not case sensitive. Text files end their lines with
a carriage return, not a line feed.
\end{itemize}

\section{The FujiNet}

A FujiNet is a network adapter for old computers. It began on the Atari
8-bit computers and now serves the Apple~II, the Coleco ADAM, the
Commodore machines, the Color Computer, and many more, each through its
own peripheral bus. To the computer it is a set of devices---disk drives,
network devices, a clock, a printer---and behind them it has WiFi and an
SD card. A disk can be an image file on the SD card or on a server on the
network; a network device can fetch a web page, pick fields out of the
JSON in it, or hold a TCP connection open.

On the TFR/911H the FujiNet gives NitrOS-9:
\begin{itemize}\setlength{\itemsep}{0pt}
\item four disk drives, \file{/X0}--\file{/X3}, whose disks are image files
the FujiNet reads from its SD card or a TNFS server;
\item network devices, \file{/N} and \file{/N1}--\file{/N5}, through which
programs ask the FujiNet to fetch from the network;
\item a place to boot from: \cmd{l2fn} boots NitrOS-9 from the FujiNet's
first disk;
\item commands to manage it, \rp{fujinet}{1} and \rp{fnconfig}{1}, and
programs that use it: \rp{fnweather}{1}, \rp{fnnews}{1},
\rp{fnstocks}{1}, \rp{fnbounce}{1}, and \rp{fnbattleship}{1}.
\end{itemize}

\subsection{The hardware}

were written with is an ESP32 development board with this module:

\subsection{The firmware}

The FujiNet runs \emph{fujinet-firmware}
(\file{github.com/FujiNetWIFI/fujinet-firmware}), one C++ code base built
for each kind of computer. For the TFR/911H it is built for the board
\texttt{fujinet-coco-devkitc-centipede}, which was added for the
Centipede, a Color Computer cartridge with an RP2350 on it. That build
selects:

\begin{keys}[1.4in]
\texttt{BUILD\_COCO} & The Color Computer's devices.\\
\texttt{DRIVEWIRE} & DriveWire as the bus: the protocol a CoCo uses to
reach a DriveWire server over a serial line.\\
\texttt{COCO\_HS\_UART} & A plain 3.3-volt serial link on the ESP32's
UART1, at a fixed 921{,}600 baud, with no line inversion and no flow
control---made for a microcontroller at the other end rather than a
CoCo's bit-banger port.\\
\end{keys}

Besides the DriveWire devices, the firmware joins your WiFi network, sets
its clock by SNTP, and runs a web server. Its web pages show and change
its settings, and its WebDAV server at \file{/dav} offers its SD card to
your computer's file manager or to \cmd{curl}. Its settings---the WiFi
network, the eight host slots, the device slots---are kept in
\file{fnconfig.ini}, on the SD card and in flash.

The firmware must read the version byte that NitrOS-9 sends after
\texttt{OP\_DWINIT} (see ``DriveWire'' below); it does since pull request
2027 to fujinet-firmware, merged in October 2026. On a DevKitC it must
also have no Safe Reset button. The board's pin map gave the button GPIO~14,
which a DevKitC leaves unconnected, and the firmware sets no pull-up on
it, so the pin floats, picks up the UART beside it, and reads as presses;
each one restarts the FujiNet, and under heavy disk traffic, as when
NitrOS-9 boots from it, that is every few seconds. The fix, which takes the
button out of the DevKitC's pin map, is pull request 2034, merged in
October 2026 as well, so firmware built from fujinet-firmware since then
has both fixes. Release jamesBrown1 has such firmware, built for
FujiNet-Flasher; the \emph{TFR Installation Guide} tells how to flash it.
\file{v4/nitros9-l2/fujinet/README.md} tells how to build and flash the
firmware.

\section{How the FujiNet Connects to the TFR/911H}

\subsection{The wiring}

The FujiNet needs three wires to the TFR/911H, wired as the Centipede's
FujiNet hat is:

\begin{tabularx}{\linewidth}{@{}l l >{\raggedright\arraybackslash}X@{}}
\toprule
\textbf{RP2350B} & \textbf{ESP32} & \textbf{Signal}\\
\midrule
GPIO~12 (UART0 TX) & GPIO~33 (UART1 RX) & Data to the FujiNet\\
GPIO~13 (UART0 RX) & GPIO~21 (UART1 TX) & Data from the FujiNet\\
GND & GND & \\
\bottomrule
\end{tabularx}

Both ends are 3.3-volt parts, so they connect directly. The link runs at
921{,}600 baud, 8 data bits, no parity, one stop bit, with no flow control:
about 92{,}000 bytes a second, or a 256-byte sector in under 3~ms. The
FujiNet's own USB port can stay plugged into your computer, which powers
it and shows its log.

\subsection{Inside the RP2350B}

The 6309 cannot see a serial port; it sees only what the RP2350B answers
on its bus. The firmware puts the link in the 6309's I/O page as a
\emph{becker port}, the simple two-register interface that CoCo
emulators give DriveWire (\file{v4\_fujinet.h}, in \file{v4/tfr911h}):

\begin{keys}[1.05in]
\file{\$FF45} & Status. Bit~1 is set when a byte from the FujiNet is
waiting.\\
\file{\$FF46} & Data. Reading takes the next byte from the FujiNet;
writing sends a byte to it.\\
\end{keys}

Emulators put the becker port at \file{\$FF41}, but that is where the
TFR/911H has its sound chip, so the port is four bytes higher, and
NitrOS-9's DriveWire modules are built to match.

The RP2350B's two cores share the work:

\par\vspace{0.6ex}\noindent\begin{minipage}{\linewidth}
\begin{exsmall}
   6309                 RP2350B core 1              RP2350B core 0              ESP32
                        (the bus loop)

  ldb $FF45  ------>  Status(): is the       <---  UART0 interrupt:      <---  UART1 TX
                      receive ring empty?          FIFO -> receive ring        GPIO 21
  ldb $FF46  ------>  Read(): pop the ring           (4K bytes)                  |
                                                                                 |  GPIO 13
  stb $FF46  ------>  Write(): push onto     --->  Pump(), in the          --->  UART1 RX
                      the transmit ring            background loop:            GPIO 33
                      (1K bytes)                   ring -> UART0 FIFO        GPIO 12
\end{exsmall}
\end{minipage}\par\vspace{0.6ex}


Core~1 answers every bus cycle of the 6309, with interrupts off, and must
never wait. So it touches only two rings in memory, never the UART. The
UART's own buffers hold only 32 bytes, which at 921{,}600 baud is about
350~microseconds; core~0's background loop can be busy longer than that,
sending the console or a disk sector to the tether over USB. So the UART's
receive interrupt, on core~0, empties the UART into a 4K receive ring as
bytes arrive, and nothing is lost. Sending has no such hurry, and the
background loop moves bytes from the transmit ring to the UART when it
comes round.

Reading \file{\$FF46} when nothing is waiting gives \file{\$FF}, and
counts an ``empty read''; a correct program checks \file{\$FF45} first.

\subsection{Watching the link}

At the \texttt{TCL>} prompt, before an OS boots:
\begin{ex}
TCL> \textbf{fujinet}
FujiNet says it is 2026-10-17 18:46:20
TCL> \textbf{fujinet stats}
rx 6 tx 1 rx_drops 0 tx_drops 0 overruns 0 empty_reads 0
\end{ex}
\cmd{fujinet} sends the DriveWire \texttt{OP\_TIME} request and prints the
FujiNet's answer, which proves both wires and the baud rate. While NitrOS-9
runs, the firmware's statistics in the tether's log, \file{v4/\_log},
include a line every ten seconds with the byte counts and the last 32
bytes on the wire, \texttt{>} for bytes to the FujiNet and \texttt{<}
for bytes from it:
\begin{exsmall}
FujiNet: 12666 out, 97015 in, 0 lost, 0 empty reads; last: >e3 >01 >52 >00 >07 >e3 ...
\end{exsmall}
\rp{info}{1} shows the same counts in its hardware report.

\subsection{Booting from the FujiNet}

The firmware holds two copies of NitrOS-9's boot track. \cmd{l2} starts the
one whose \file{Boot} module reads \file{OS9Boot} from EmuDsk, the
tether's disk. \cmd{l2fn} starts the one whose \file{Boot} module,
\file{boot\_dw}, reads it from DriveWire drive~0---the FujiNet's first
device slot. When the FujiNet powers up, it puts its own CONFIG disk in
that slot, so \cmd{l2fn} first mounts whatever the slot names, with the
FujiNet's own commands (\texttt{FUJI\$MountHost}, then
\texttt{FUJI\$MountImage}; see ``Programming the FujiNet''):
\begin{ex}
TCL> \textbf{l2fn}
FujiNet slot 1: level2-fn.dsk
...
NitrOS-9 Level 2 on the TFR/911H
\end{ex}
The \file{OS9Boot} on that disk makes \file{/X0} the system disk,
\file{/DD}. The tether's disk is still there, as \file{/H0}.
\rp{fujinet}{4} tells how to make such a disk and put it on the FujiNet.

\section{DriveWire}

DriveWire, from Cloud-9, is the protocol a Color Computer uses to reach a
DriveWire server on another computer: a serial line, and \emph{transactions} that each begin with a
one-byte opcode from the CoCo. The CoCo always asks and the server answers;
the server never speaks first. These are the transactions the TFR/911H
uses:

\begin{tabularx}{\linewidth}{@{}l l >{\raggedright\arraybackslash}X@{}}
\toprule
\textbf{Opcode} & \textbf{Name} & \textbf{What it does}\\
\midrule
\file{\$D2} & \texttt{OP\_READEX} & Read a sector: drive and 24-bit LSN out; 256 bytes back; a checksum out; a status byte back\\
\file{\$F2} & \texttt{OP\_REREADEX} & The same, after a checksum error\\
\file{\$57} & \texttt{OP\_WRITE} & Write a sector: drive, LSN, 256 bytes and a checksum out; a status byte back\\
\file{\$23} & \texttt{OP\_TIME} & Six bytes back: year since 1900, month, day, hour, minute, second\\
\file{\$5A} & \texttt{OP\_DWINIT} & The driver's version byte out; the server's version byte back\\
\file{\$45} & \texttt{OP\_SERINIT} & Open a virtual channel (\file{/N1} is channel~1)\\
\file{\$C4} & \texttt{OP\_SERSETSTAT} & A SetStat on a virtual channel: \texttt{SS.Open}, \texttt{SS.ComSt} (with 26 bytes of path options), \ldots\\
\file{\$E2} & \texttt{OP\_FUJI} & A FujiNet management command (below)\\
\file{\$E3} & \texttt{OP\_FUJINET} & A FujiNet network-device command (below)\\
\bottomrule
\end{tabularx}

Reading a sector looks like this on the wire (the numbers are an
example). The checksum is the sum of
the 256 bytes, as a 16-bit number; if the server's sum differs, it answers
\texttt{E\$CRC} and the driver asks again with \texttt{OP\_REREADEX}:
\begin{exsmall}
  6309 -> FujiNet:   D2  00  00 00 3C              OP_READEX, drive 0, LSN $00003C
  FujiNet -> 6309:   ... 256 bytes of sector $3C ...
  6309 -> FujiNet:   7A 41                         the checksum it computed
  FujiNet -> 6309:   00                            status: no error
\end{exsmall}

The FujiNet adds two opcodes of its own, \file{\$E2} and \file{\$E3},
which are how programs reach its management functions and its network
devices. Their replies come back as raw bytes, outside DriveWire's
virtual-channel framing.

A DriveWire link has no framing or resynchronization: both ends must agree
on the length of every transaction. A server that reads one byte too few
takes the next byte for an opcode, and both ends are lost. That is what
happened before the FujiNet's firmware was fixed to read the version byte
after \texttt{OP\_DWINIT}: it took that byte for an opcode, threw away the
\texttt{OP\_SERINIT} and \texttt{OP\_SERSETSTAT} already waiting behind it,
and the 6309 waited for a reply that never came. On a real CoCo's slower
link the next command had not yet arrived, and survived.

\subsection{Synchronous, with interrupts masked}

Every DriveWire exchange in NitrOS-9 is synchronous: the driver masks the
6309's interrupts, writes its request, and polls for each byte of the
reply. Nothing else can use the wire meanwhile, so no one else's bytes
are taken for yours. The cost is that the clock and the keyboard wait too:
a request that keeps the FujiNet busy for a second stops NitrOS-9 for a
second.

DriveWire's \emph{virtual-serial poller} breaks this rule. In a normal
DriveWire system \file{dwio} installs a routine on the 60~Hz clock that
asks the server, between other work, whether a virtual channel has data
(\texttt{OP\_SERREAD}). The FujiNet's replies are raw bytes, not channel
data, and a poll between a request and its reply would take them. So
\file{dwio} is built with \texttt{DWIO\_NO\_VIRQ=1}, which leaves the
poller out. \file{/N1} still opens and closes, but programs talk through
it only with \texttt{SS.Fuji}.

\subsection{Level 1 and Level 2}

Like most of NitrOS-9, the FujiNet code is written once for both levels:
its sources live in the Level~1 directories of the NitrOS-9 tree, and
conditional assembly on \texttt{Level} picks what differs. The commands
and libraries are the same source for both, linked with the system
definitions for one level or the other. The drivers differ in how they
reach memory:

\begin{description}\setlength{\itemsep}{0.5ex}
\item[\sans{Level 1}] has one 64K address space. \file{scdwv}'s
\texttt{SS.Fuji} hands the caller's request buffer straight to
\texttt{DWWrite}, and has \texttt{DWRead} put the reply straight into the
caller's reply buffer.

\item[\sans{Level 2}] gives each process its own address space, which the
driver, running in the system's address space, cannot address. So
\texttt{SS.Fuji} takes a 512-byte buffer from system memory
(\texttt{F\$SRqMem}), copies the request into it from the caller's task
with \texttt{F\$Move}, makes the exchange from that buffer, copies the
reply back to the caller's task with \texttt{F\$Move}, and returns the
buffer (\texttt{F\$SRtMem}).
\end{description}

On the TFR/911H, Level~1 is TurbOS, a 64K image in the firmware with no
disk or DriveWire modules, so the FujiNet is a Level~2 feature here. The
same Level~1 code runs elsewhere: the \file{dillera/nitros9} tree, where
it was written, has a Level~1 recipe that boots a Wildbits Jr2 from a
FujiNet over its UART.

\section{Programming the FujiNet}

A program reaches the FujiNet by opening \file{/N1} and making
\texttt{SS.Fuji} SetStat calls on the path. Each call is one complete
exchange: a request sent, and a reply of a known length read back. Two
libraries build the requests, one for the FujiNet's management commands
and one for its network devices. They are in \file{fujinet/lib}, in
\file{v4/nitros9-l2}.

\subsection{The SS.Fuji call}

\begin{keys}[1.05in]
\texttt{A} & The path to \file{/N1}.\\
\texttt{B} & \texttt{SS.Fuji} (\file{\$E2}).\\
\texttt{X} & A parameter block: the length of the reply wanted (two bytes,
high byte first), then the request.\\
\texttt{Y} & The length of the parameter block: 2 plus the request's
length.\\
\texttt{U} & Where the reply goes. Not used if the reply length is 0.\\
\end{keys}
The request and the reply may each be up to 512 bytes
(\texttt{FUJI\$MaxTran}). On success the carry is clear. Because a program
keeps its data pointer in \texttt{U}, save it around the call, as the
libraries do:
\begin{exsmall}
* Ask the FujiNet for the status of the last management command: send
* [OP_FUJI, FUJI$GetError] and read one byte back into fbstat.
FBErr               pshs      a,x,y,u
                    leax      fbsmall,u
                    ldd       #1                  one byte of reply wanted
                    std       ,x
                    ldd       #OP_FUJI*256+FUJI$GetError
                    std       2,x                 the request: two bytes
                    ldy       #4                  2 + the request
                    lda       fbpath,u            the path to /N1
                    ldb       #SS.Fuji
                    pshs      u
                    leau      fbstat,u            the reply goes here
                    os9       I$SetStt
                    puls      u
\end{exsmall}

Ask for exactly as many bytes as the command sends back. If you ask for
more, the 6309 waits for bytes that will never come---with interrupts
masked---and only a reset ends the wait.

\subsection{Management commands}

A management command is \texttt{OP\_FUJI} (\file{\$E2}), a command byte,
and its parameters. The FujiNet carries it out and keeps the outcome; the
program then asks for the outcome with \texttt{FUJI\$GetError}, which
returns \file{\$01} if it worked, and for any data with
\texttt{FUJI\$GetResponse}. \file{lib/fuji.as} does this:

\begin{keys}[1.05in]
\texttt{NOpen} & Open \file{/N1}; keep the path.\\
\texttt{FBReady} & Ask until the FujiNet says it is ready
(\texttt{FUJI\$Ready}).\\
\texttt{FBCmd} & Send a command, then fetch its outcome; carry set if it
failed.\\
\texttt{FBErr} & Fetch the outcome of the last command.\\
\texttt{FBRead} & Fetch the data of the last command.\\
\end{keys}

The commands are defined in \file{fujinet/defs/drivewire.d}:

\begin{tabularx}{\linewidth}{@{}l l >{\raggedright\arraybackslash}X@{}}
\toprule
\textbf{Byte} & \textbf{Name} & \textbf{What it does}\\
\midrule
\file{\$E8} & \texttt{FUJI\$GetAdapterCfg} & The adapter's settings: SSID, host name, IP, gateway, netmask, DNS, MAC, firmware version (140 bytes)\\
\file{\$FA} & \texttt{FUJI\$GetWifiStatus} & Whether the WiFi is connected\\
\file{\$FD}, \file{\$FC} & \texttt{FUJI\$ScanNetworks}, \texttt{GetScanResult} & Scan for WiFi networks; one result\\
\file{\$FE}, \file{\$FB} & \texttt{FUJI\$GetSSID}, \texttt{SetSSID} & The WiFi network and password\\
\file{\$F4}, \file{\$F3} & \texttt{FUJI\$ReadHostSlots}, \texttt{WriteHostSlots} & The eight host slots, 32 bytes each\\
\file{\$F9}, \file{\$E6} & \texttt{FUJI\$MountHost}, \texttt{UnmountHost} & Connect to a host, or stop\\
\file{\$F7}, \file{\$F6}, \file{\$F5} & \texttt{FUJI\$OpenDir}, \texttt{ReadDirEntry}, \texttt{CloseDir} & List a directory on a host\\
\file{\$F2}, \file{\$F1} & \texttt{FUJI\$ReadDevSlots}, \texttt{WriteDevSlots} & The device slots: host slot, mode, and a 36-byte file name each\\
\file{\$E2}, \file{\$DA} & \texttt{FUJI\$SetDevicePath}, \texttt{GetDevicePath} & One device slot's image\\
\file{\$F8}, \file{\$E9} & \texttt{FUJI\$MountImage}, \texttt{UnmountImage} & Mount or eject a device slot's image\\
\file{\$E7} & \texttt{FUJI\$NewDisk} & Make a new, empty disk image\\
\file{\$02}, \file{\$01} & \texttt{FUJI\$GetError}, \texttt{GetResponse} & The outcome, and the data, of the last command\\
\file{\$00} & \texttt{FUJI\$Ready} & One byte back, nonzero when the FujiNet is ready\\
\bottomrule
\end{tabularx}

All of \cmd{fnstatus} is a page of code. After opening \file{/N1}, it asks
for the adapter's settings and prints them:
\begin{exsmall}
__start             lbsr      NOpen               open /N1
                    lbcs      errex
                    sta       netpath,u
                    lbsr      FBReady             wait until the FujiNet answers
                    lbcs      closeerr
                    leax      request,u
                    ldd       #OP_FUJI*256+FUJI$GetAdapterCfg
                    std       ,x
                    ldy       #2
                    lbsr      FBCmd               send it; check the outcome
                    lbcs      closeerr
                    leax      config,u
                    ldy       #ADPCFGSZ           140 bytes of settings
                    lbsr      FBRead
                    lbcs      closeerr
                    ...                           print config+CFGVER, config+CFGHOST, ...
\end{exsmall}

\subsection{The network device}

The FujiNet's network devices (its \texttt{N:} devices) fetch from the
network for the computer. A network command is \texttt{OP\_FUJINET}
(\file{\$E3}), a unit number (\file{fnnet} uses unit~1), a command byte, two
parameter bytes, and, for some commands, a 256-byte \emph{device spec},
padded with zeros:

\par\vspace{0.6ex}\noindent\begin{minipage}{\linewidth}
\begin{exsmall}
   E3  01  'O'  04  00   N:https://api.open-meteo.com/v1/forecast?latitude=...  00 00 ...
   |   |    |   |   |    '--------------- device spec, 256 bytes -------------------'
   |   |    |   |   '-- translation: 0, none
   |   |    |   '------ mode: 4, read
   |   |    '---------- command: open
   |   '--------------- unit 1
   '------------------- OP_FUJINET
\end{exsmall}
\end{minipage}\par\vspace{0.6ex}


\begin{tabularx}{\linewidth}{@{}l l >{\raggedright\arraybackslash}X@{}}
\toprule
\textbf{Command} & \textbf{Parameters} & \textbf{What it does}\\
\midrule
\texttt{'O'} & mode, translation; spec & Open the URL in the spec. Mode 4 is read, for HTTP GET\\
\file{\$FC} & 1, 0 & Channel mode: 1 makes the device parse what it fetched as JSON\\
\texttt{'P'} & & Parse: fetch the URL, and parse the JSON\\
\texttt{'Q'} & ; spec & Query: the spec is a path into the JSON, such as \texttt{/current/temperature\_2m}\\
\texttt{'R'} & length (2) & Read up to \var{length} bytes of the open device---after \texttt{'Q'}, the value\\
\texttt{'S'} & & Status: bytes waiting, connected, and the last error\\
\texttt{'C'} & & Close\\
\file{\$02} & & The outcome of the last command, one byte: \file{\$01} if it worked\\
\file{\$01} & length (2) & The data of the last read, padded with zeros to \var{length}\\
\bottomrule
\end{tabularx}

The device does more than this---writing, and other protocols in the
spec, such as TCP, UDP, FTP, TNFS, and SSH---but HTTP and JSON are what
\file{lib/fnnet.as} provides:

\begin{keys}[1.05in]
\texttt{FNNetInit} & Open \file{/N1}, and give the FujiNet a moment.\\
\texttt{FNNetOpen} & Open the URL at \texttt{X} (up to 255 characters,
beginning \texttt{N:}).\\
\texttt{FNNetParse} & Select JSON mode and parse what the URL returns,
then wait ten seconds, since an HTTPS request can take the ESP32
several, before the first query.\\
\texttt{FNNetQuery} & Look up the JSON path at \texttt{X}; put the value,
as text, at \texttt{Y}, at most \texttt{B} bytes with its terminating
zero.\\
\texttt{FNNetClose} & Close the device.\\
\end{keys}

So fetching one value from a web service is four calls:
\begin{exsmall}
                    lbsr      FNNetInit           once, at the start: open /N1
                    leax      url,pcr
                    lbsr      FNNetOpen
                    lbsr      FNNetParse
                    leax      query,pcr           "/city"
                    leay      city,u              33 bytes, in the program's data
                    ldb       #33
                    lbsr      FNNetQuery          city now holds "Philadelphia"
                    lbsr      FNNetClose
   ...
url                 fcn       "N:http://ip-api.com/json/?fields=status,city"
query               fcn       "/city"
\end{exsmall}
(Check the carry after each call; the real programs do.)

\subsection{Building a program}

The FujiNet programs are LWASM object files, linked with LWLINK into OS-9
modules. A program has three sections: \texttt{\_\_os9}, with its module
type, edition and stack size; \texttt{bss}, its variables, which the
linker puts in the process's data area, reached through \texttt{U}; and
\texttt{code}. Execution starts at \texttt{\_\_start}. The build links each
one with the libraries:
\begin{exsmall}
$ lwasm --6309 --format=obj -DANSI=1 -Ifujinet/lib -Ifujinet/defs -I$(NITROS9_DIR)/defs \textbackslash{}
      -o build/fn/fnhello.o fujinet/cmds/fnhello.as
$ cd build/fn && lwlink --format=os9 -o fnhello fnhello.o fnnet.o fuji.o ../sys.o ../alib.a
\end{exsmall}
The Makefile in \file{v4/nitros9-l2} does this for every file in
\file{fujinet/cmds}: put \file{fnhello.as} there, type \type{make}, and
\cmd{fnhello} is in \file{/DD/CMDS} on the new disk (\type{make install}
puts it on yours). \file{alib} gives you \texttt{PRINTS}, \texttt{PUTS},
\texttt{DEC\_BIN}, and NitrOS-9's other assembly-language helpers.

\section{An Example: fnwx}

\cmd{fnwx} (\file{fujinet/cmds/fnwx.as}, 1{,}213 lines) finds where
you are from your network's public address, and shows the weather there.
It was the first \cmd{fnweather}, until that was written again in C, with
icons and the week's forecast (see Programs in C); it is kept, as
\cmd{fnwx}, for this walk through. It uses two free web services, neither of which needs a key:
\texttt{ip-api.com} for the location, and Open-Meteo for the weather.

\subsection{The plan}

\begin{enumerate}\setlength{\itemsep}{0pt}
\item Put the terminal in raw mode, and open \file{/N1} (\texttt{FNNetInit}).
\item \emph{Locate}: fetch \texttt{ip-api.com}, and query the city, region,
country, latitude, and longitude.
\item Choose Fahrenheit and miles in the United States, Liberia, and
Myanmar, Celsius and kilometres elsewhere.
\item \emph{Fetch}: build an Open-Meteo URL from the latitude and
longitude, and query the conditions---twice, since one URL with every
field would not fit in the 256-byte device spec.
\item Draw the screen, and wait for a key: \key{R} fetches again, \key{U}
changes the units, \key{L} locates again, \key{Q} quits.
\end{enumerate}

\subsection{Locating}

The location request names only the fields it wants, so the reply is
short:
\begin{exsmall}
ipURL     fcn   "N:http://ip-api.com/json/?fields=status,city,regionName,countryCode,lon,lat"
\end{exsmall}
and the answer is a small JSON object, for example:
\begin{exsmall}
\{"status":"success","countryCode":"US","regionName":"Pennsylvania",
 "city":"Philadelphia","lat":39.98,"lon":-75.23\}
\end{exsmall}
\texttt{FetchLocation} opens it, parses it, checks that \texttt{/status}
is \texttt{success}, and copies each field into a buffer of its own:
\par\vspace{0.6ex}\noindent\begin{minipage}{\linewidth}
\begin{exsmall}
FetchLocation       ...
                    leax      ipURL,pcr
                    lbsr      FNNetOpen
                    lbcs      FetchAbort
                    lbsr      FNNetParse
                    lbcs      FetchAbort
                    leax      qStatus,pcr         "/status"
                    leay      linebuf,u
                    ldb       #16
                    lbsr      FNNetQuery
                    lbcs      FetchAbort
                    leax      linebuf,u
                    leay      success,pcr         "success"
                    lbsr      StrEqual
                    bne       FetchLocationBad
                    leax      qCity,pcr           "/city"
                    leay      city,u
                    ldb       #33
                    lbsr      FNNetQuery
                    ...                           /regionName, /countryCode, /lat, /lon
                    lbsr      FNNetClose
                    rts
\end{exsmall}
\end{minipage}\par\vspace{0.6ex}

The values arrive as text, just as they appear in the JSON: the latitude is
the string \texttt{39.98}, ready to be put into the next URL.

\subsection{Fetching the weather}

\texttt{BuildWeatherURL} joins the pieces in a 256-byte buffer:
\par\vspace{0.6ex}\noindent\begin{minipage}{\linewidth}
\begin{exsmall}
meteoHead      fcn  "N:https://api.open-meteo.com/v1/forecast?latitude="
meteoLongitude fcn  "&longitude="
currentTail1   fcn  "&timezone=auto&forecast_days=1&current=temperature_2m,
                     apparent_temperature,relative_humidity_2m,weather_code"
imperialTemp   fcn  "&temperature_unit=fahrenheit"

BuildWeatherURL     pshs      x                   X = the tail to end with
                    leay      urlbuf,u
                    leax      meteoHead,pcr
                    lbsr      CopyZAdvance        copy, leaving Y at the end
                    leax      latitude,u
                    lbsr      CopyZAdvance
                    leax      meteoLongitude,pcr
                    lbsr      CopyZAdvance
                    leax      longitude,u
                    lbsr      CopyZAdvance
                    puls      x
                    lbsr      CopyZAdvance
                    clr       ,y
                    rts
\end{exsmall}
\end{minipage}\par\vspace{0.6ex}

then \texttt{FetchCurrentOne} opens it, parses it, and queries five
values under \texttt{/current}: the time, \texttt{temperature\_2m},
\texttt{apparent\_temperature}, \texttt{relative\_humidity\_2m}, and
\texttt{weather\_code}. A second URL asks for the pressure and the wind.

Here is one of those queries on the wire, from the TFR/911H's log: the
wind direction. After the query (\texttt{'Q'}, \file{\$51}, with its
path), the program reads up to seven bytes of the value, fetches them,
closes the device, and checks the outcome:
\begin{exsmall}
>e3 >01 >52 >00 >07                  'R': read, up to 7 bytes
>e3 >01 >01 >00 >07                  $01: the data, 7 bytes
<33 <34 <31 <0a <00 <00 <00          "341", a line feed, and padding
>e3 >01 >43 >00 >00                  'C': close
>e3 >01 >02 >00 >00                  $02: the outcome?
<01                                  $01: it worked
\end{exsmall}
\texttt{FNNetQuery} copies the value up to the line feed, so the program
has the string \texttt{341}, which \texttt{WindDirection} turns into a
compass point with \texttt{DEC\_BIN} and a few comparisons: 341~degrees
is north.

\subsection{Turning numbers into words}

Open-Meteo gives the sky as a WMO weather code. \texttt{WeatherDescription}
turns it into words the same way:
\begin{exsmall}
WeatherDescription  lbsr      DEC_BIN             the code, as text, into D
                    bcs       DescUnknown
                    cmpd      #0
                    beq       DescClear           "Clear sky"
                    cmpd      #1
                    beq       DescMainly          "Mainly clear"
                    ...
                    cmpd      #58
                    blo       DescDrizzle         51-57: "Drizzle"
                    ...
\end{exsmall}

\subsection{The screen}

\cmd{fnwx} reads keys one at a time, without echo: it copies its
standard input's path options with \texttt{SS.Opt}, turns off echo, auto
line feed, and paging (\texttt{PD.EKO}, \texttt{PD.ALF}, \texttt{PD.PAU}),
and puts them back when it ends. It draws with a handful of
routines: clear the screen, move the cursor (\texttt{TAt}, column in
\texttt{A} and row in \texttt{B}), cursor on and off, and reverse video.
For a Color Computer~3 window they send its control codes; built with
\texttt{ANSI=1}, as on the TFR/911H, they come from
\file{fujinet/lib/fnansi.as} and send ANSI sequences to the tether's
terminal instead. The rest of the program does not know the difference.

\subsection{Writing your own}

Any web service that answers a GET request with JSON can be used the same
way: build the URL, open it, parse it, query the fields you want, close
it. Some things to remember:

\begin{itemize}\setlength{\itemsep}{0pt}
\item A device spec, with its \texttt{N:} and its URL, is at most 255
characters. Ask the service for only the fields you need, as
\cmd{fnwx} does; split the request in two if you must.
\item A query's value is text, as it appears in the JSON. Give
\texttt{FNNetQuery} a buffer big enough for the longest value, with its
zero.
\item An array element is a path too: \texttt{/daily/time/0} is the first
element of \texttt{daily.time}.
\item Each exchange stops NitrOS-9 while it runs, and each
\texttt{FNNetParse} takes ten seconds. Fetch when the user asks, not in a
loop.
\item Close what you open, even when a query fails, as
\texttt{FetchAbort} does; a device left open keeps the FujiNet's
connection, and the next program's replies may not be what it expects.
\end{itemize}

\cmd{fnconfig} is the other large example: the management commands for
hosts, device slots, directories, and WiFi, behind a full-screen
interface.

\section{Programs in C}

Many of the FujiNet's programs for other computers are written in C,
against \emph{fujinet-lib}, the FujiNet's C library, which has the same
calls on every computer. Those for the Color Computer are compiled with
CMOC, which compiles for OS-9 too. \file{fujinet/fujinet-lib}, in
\file{v4/nitros9-l2}, is fujinet-lib for NitrOS-9, and \file{fujinet/c}
is a terminal to draw on. With them, five of the Color Computer's
programs became NitrOS-9 commands, their logic unchanged:
\rp{fnnews}{1}, from \texttt{fujinet-news}, \rp{fnstocks}{1}, from
\texttt{fujinet-stocks}, \rp{fnbounce}{1}, from
\texttt{bounce-world-client}, \rp{fnweather}{1}, from
\texttt{fujinet-weather}, and \rp{fnbattleship}{1}, from
\texttt{fujinet-battleship}.

\subsection{fujinet-lib for NitrOS-9}

fujinet-lib keeps what is the same on every computer in \file{common},
and what each computer's bus needs in \file{bus/}\var{platform}. On a CoCo
the bus calls the DriveWire ROM: \texttt{dwwrite} sends bytes and
\texttt{dwread} reads the reply, and the rest of the CoCo's
bus---\texttt{fuji\_bus\_call}, \texttt{bus\_ready}, the calls for a
command's status and its data---is built on those two.
\file{fujinet/fujinet-lib} has fujinet-lib v5.0.1's \file{include} and
\file{common}, unchanged, and a bus for NitrOS-9, \file{bus/os9}, made from
the CoCo's:

\begin{keys}[1.4in]
\file{ssfuji.c} & Opens \file{/N1}, and makes the \texttt{SS.Fuji}
calls.\\
\texttt{dwwrite} & Queues its bytes.\\
\texttt{dwread} & Sends what is queued and reads the reply, in one
\texttt{SS.Fuji} call. Every fujinet-lib command ends with a read, of its
status at least, so nothing is left queued.\\
\file{network\_bus.c} & Reads at most 512 bytes at a time, as much as
\texttt{SS.Fuji} carries; \texttt{network\_read} asks again for the
rest.\\
\file{fuji\_bus\_call.s} & The CoCo's, made position independent, as an
OS-9 module must be: \texttt{LBSR} for its calls, its variables through
\texttt{Y}, and its table through \texttt{PCR}.\\
\file{network\_proceed.c} & A becker port has no proceed line: poll
\texttt{network\_status} instead.\\
\end{keys}

The rest of the bus is the CoCo's, unchanged, and so is the protocol on
the wire, since the FujiNet runs the same firmware. Every \texttt{fuji\_*}
and \texttt{network\_*} call of fujinet-lib is there---HTTP and JSON, TCP
and UDP, app keys (up to 64 bytes the FujiNet keeps on its SD card for a
program), host and device slots, directories, the clock---and a program
written with fujinet-lib for the CoCo builds for NitrOS-9. \file{README.md}
in the directory tells how to bring in a newer fujinet-lib.

A call is a few \texttt{SS.Fuji} exchanges. Each command is preceded by
\texttt{bus\_ready} (\file{\$E2 \$00}, which the FujiNet answers with one
byte) and followed by \file{\$02}, its outcome; \texttt{network\_open},
for instance, sends \texttt{'O'} with its spec. fujinet-lib asks for the
outcome of a JSON parse (\texttt{'P'}) at once, where \file{fnnet.as}
sleeps ten seconds first. The FujiNet does not read the question until it
has fetched and parsed the document, and the becker port has no timeout,
so the call takes as long as the fetch and no longer. NitrOS-9 stops while
it waits.

These are the four calls of the last section, in C:
\begin{exsmall}
#include "fujinet-network.h"

char city[64];
char url[] = "N:http://ip-api.com/json/?fields=status,city";

if (network_open(url, OPEN_MODE_HTTP_GET, OPEN_TRANS_NONE) == FN_ERR_OK
    && network_json_parse(url) == FN_ERR_OK)
    network_json_query(url, "/city", city);       /* "Philadelphia" */
network_close(url);
\end{exsmall}

\subsection{The terminal}

The Color Computer's programs draw on its screen: \texttt{printf} at the
cursor, and reverse video for the line that is selected, made by flipping
the attribute bytes of a row in screen memory. \file{term.c} draws the same
things on the tether's terminal with ANSI sequences. It keeps a copy of the
screen, a byte for each place, with bit~7 set where it is in reverse video,
and a byte of its colors, so that \texttt{term\_invert\_row} can flip a
row and send it again; \texttt{term\_color} sets the colors of what
follows, from the terminal's eight and their bright versions. It
reads keys raw from \file{/term}, sets bit~7 of \file{\$FF42}, as
\rp{vi}{1} does, so that the arrow keys arrive as the tether sends them,
and takes \key{Esc}, and \key{Ctrl/C}, which arrives as a signal, as the
Color Computer's \key{BREAK}.

A program that redraws the screen many times a second, as a CoCo program
does by drawing on a second screen and then showing it, calls
\texttt{term\_frame} to start a frame, which is drawn in the copy alone,
and again to end it, which sends only the places that changed; only the
rows the frame wrote are compared. A place can hold one of the
line-drawing and block characters (\texttt{TG\_HLINE} and the rest), which
\file{term.c} sends as UTF-8. And what it sends goes straight to the
console's 6850, at \file{\$FF15}, not through SCF, which takes some 300
microseconds a character: the firmware's 6850 is always ready for another
character, and holds the 6309 while its buffer to the tether is full.

\subsection{The five programs}

\cmd{fnnews} is the Color Computer client of \texttt{fujinet-news}. Its
topics, pages of headlines, and pages of a story are the same state
machines as on the CoCo, laid out as on a CoCo~3's 80-column screen. The
news server formats each page to fit; the program puts the screen's width
and height in the URL:
\begin{exsmall}
N:HTTPS://FUJINET.ONLINE/8bitnews/news.php?t=lf&ps=80x21&l=6&p=1&c=top
\end{exsmall}
The CoCo's screen code, \file{cocotext.c} and \file{bar.c}, became
\file{fujinet/news/screen.c}, a page of calls to \file{term.c}, which also
draws the title bars, rules, and colors, and the page \key{I} shows,
about the program and the server.

\cmd{fnstocks} is \texttt{fujinet-stocks}, written for many computers at
once: its own code calls the \texttt{conio} routines and the C library,
and each computer has a directory of headers and routines that provide
them. NitrOS-9 has one, \file{os9}, beside \file{coco}. Its \file{conio.h}
sends \texttt{gotoxy}, \texttt{revers}, \texttt{cputs}, and the rest to
\file{term.c}; its \file{time.h} makes \texttt{clock} from
\texttt{F\$Time}. Of the program's own files, a few lines changed: an
80-column screen, \key{Esc} as the name of \key{BREAK}, the ticker
drawn only when it moves, since on a terminal each row drawn goes down the
wire, and colors, through a \texttt{COLOR} macro that is empty on other
computers. The stock list is kept in two app keys of creator \file{\$0901}, the
ones the other computers' versions use, so a FujiNet shared between
computers has one list.

\cmd{fnbounce} is the client of Bounce World, Mark Fisher's
\texttt{bounce-world-client}, which is written for many computers at once
too: NitrOS-9's directory, \file{os9}, is beside \file{coco}. A server
moves shapes about a world made of the screens of all its clients, and
sends each client, ten times a second over a TCP connection, the shapes on
its screen. The CoCo draws them on a 42-column screen. Here each place of
the world is two columns of the terminal, so that a round shape looks
round; the line-drawing characters keep their vertical strokes in the left
column and carry their horizontal ones through the right, so that the
lines still join; or, set on its title screen, the world is 80 places
wide, a place to a column. The screens before the world---the title, with
its logo and settings, and the kinds of shape---are NitrOS-9's own
(\file{os9/title.c}), drawn for an 80-column terminal. Of the program's own
files, a few lines changed (\texttt{BUILD\_OS9}): the places and a color
for each kind of shape, calls to those screens, and the main loop, which
sends the next request before it draws, so that the FujiNet and the
server are at work while the 6309 draws.

\cmd{fnweather} is the Color Computer client of \texttt{fujinet-weather}:
its requests to \texttt{ip-api.com} and Open-Meteo, its descriptions of
the WMO weather codes and its choice of icon for each, with a screen of
its own for the terminal (\file{fujinet/weather}). It asks for the
weather in three requests, not the CoCo's seven, the fewest whose URLs
fit a device spec of 255 characters, and in metric units, which it
converts itself, in integers, since CMOC has no floating point under
OS-9; so \key{U} needs no request. Its icons are pixel art, two pixels to
a character, drawn with half blocks in the terminal's colors, one as the
foreground and one as the background where both halves are colored; a
Python program, \file{icons.py}, makes them from shapes---a sun, clouds of
overlapping discs, drops, flakes, a bolt---into \file{icondata.h}. What
it fetched last is kept in \file{/DD/SYS/fnweather.dat}, with the place
and the units, so that it shows them at once, and fetches again only when
they are half an hour old.

\cmd{fnbattleship} is \texttt{fujinet-battleship}, Eric Carr's and
Thomas Cherryhomes' game of sea battle, whose game is the same C on every
computer, with a directory for each computer's screen, keys, and sound;
NitrOS-9's, \file{os9}, is beside \file{coco}. The server sends its state
as a C structure, ready to read into memory, and CMOC lays structures out
as the server expects, a byte at a time with no padding. On the CoCo the
boards are bitmaps; here a square is two columns of the terminal, so that
it is square, the water blue with waves, the ships in grey half blocks,
hits a fire of shaded blocks in red and yellow, misses a white ring, and
the cursor a blinking reticle. Two players have their boards side by
side, with coordinates, and whose turn it is between them; three or four
have a quarter of the screen each. A coordinate can be typed, a letter
and a digit, as well as aimed at with the arrows, and the ship being
placed is marked in the fleet beside the board (\texttt{BUILD\_OS9} in
\file{gamelogic.c}). One change is for every computer: when a turn's time
runs out, the program asks the server for the state at once. Upstream's
waited out the time again, and again, while the server had moved for
the player. Its sounds, played on the SN76489, are a sonar's
ping for your turn, a shell's whistle, explosions---noise on the noise
voice at the pitch of a silent tone voice, swept down---and splashes.
\file{term.c} keeps 31 graphics characters at most, and lets a program
have its own (\texttt{term\_glyphs}); \cmd{fnbattleship} has the double
lines, shades, arrows, and rings it draws with. Its title has a
battleship of pixel art, made by \file{shipart.py} as \cmd{fnweather}'s
icons are.

\subsection{Building and testing}

\type{make fujinet-lib} compiles fujinet-lib and puts it in
\file{build/fnlib/libfujinet.a}. The Makefile compiles each program's C
files with \texttt{cmoc --os9 -c}, and links them with \file{term.o} and
the library, from which only what the program uses is taken:
\begin{exsmall}
$ cmoc --os9 --cpp=$PWD/fujinet/fujinet-lib/cmoc-cpp -Ifujinet/fujinet-lib/include -Ifujinet/c \textbackslash{}
      --function-stack=0 --add-os9-stack-space=2048 -DBUILD_OS9 -c -o build/fn/news/main.o \textbackslash{}
      fujinet/news/main.c
$ cd build/fn && cmoc --os9 -o fnnews news/*.o c/term.o -L../fnlib -lfujinet
\end{exsmall}
fujinet-lib indents some of its preprocessor directives, which macOS's
\cmd{cpp}, a traditional preprocessor, skips; \file{cmoc-cpp} gives CMOC
the C compiler's own preprocessor instead.
The stack space is set when the file with \texttt{main} is compiled; given
when linking, it is ignored, and the program has no room for its stack.
CMOC's OS-9 programs keep their stack above their variables, in the same
data area. And \texttt{term\_printf} does its own formatting, because
CMOC's \texttt{vsprintf} does not work in an OS-9 program (in version
0.1.97 it writes to standard output, and the stack then overflows);
\texttt{printf} and \texttt{sprintf} do.
Two more of CMOC's ways showed on the board, in \cmd{fnweather}. A
\texttt{const} array of strings, such as \texttt{const char t[10][14][15]},
is kept in the data area with the variables that have values to start
with, where a \texttt{const char t[]} is kept in the module; and the
module's header, which tells OS-9 how much memory the program needs,
counts the variables that start at zero and the stack, but not those. A
big table of strings therefore leaves the stack no room, and
\cmd{fnweather}'s icons are each one long string. And the product of an
\texttt{unsigned char} and a constant that fits in one is kept to eight
bits: \texttt{icon * 196} has to be written \texttt{(word) icon * 196}.
\type{make build/fnnews-host} and \type{make build/fnstocks-host} build
them for the computer the tether runs on, with
\file{fujinet/c/host/fujinet-host.c} in place of fujinet-lib: \cmd{curl} fetches, \cmd{python3} answers the
JSON queries, and app keys are files. The screens are the same, so a
change can be tried there before it goes to the board.
\type{make build/fnweather-host} builds \cmd{fnweather}, which keeps its
cache in \file{fnweather.dat} there, or in \texttt{\$FNWEATHER\_CACHE}.
\type{make build/fnbattleship-host} builds \cmd{fnbattleship}, which plays
on the real server.
\type{make build/fnbounce-host} builds \cmd{fnbounce} the same way, with
TCP: it is compiled as for CMOC, with stand-ins for CMOC's \file{cmoc.h}
and \file{coco.h} in \file{fujinet/bounce/host}, so that it takes the
same paths as on the board, and plays against a real server.

\refentry{beep}{1}{ring the bell}
\begin{refpage}
\rh{Name} \cmd{beep} -- ring the bell
\rh{Syntax} \cmd{beep}
\rh{Description}
The \cmd{beep} command writes a bell character (\file{\$07}) to standard
output. The terminal the tether runs in rings its bell, and the TFR/911H

power on).

\rh{Examples}

\refentry{fnbattleship}{1}{Fuji Battleship}
\begin{refpage}
\rh{Name} \cmd{fnbattleship} -- Fuji Battleship, through the FujiNet
\rh{Syntax} \cmd{fnbattleship}
\rh{Description}
The \cmd{fnbattleship} command plays Fuji Battleship, a game of sea
battle for up to four players, on a server on the Internet, against
people on other computers or the server's robots. Each player places five
ships on a board of ten squares by ten; then they take turns, and a shot
at a square is a shot at that square on every other player's board. The
last with a ship afloat wins.

\cmd{fnbattleship} starts with its title, which shows its version and the
day it was built. The first time, it asks for a name, which the FujiNet
keeps for the games of its lobby, and shows how to play. Then it lists
the server's tables: some for people, and some with robots
(\texttt{ai~-~1~on~1}, \texttt{ai~-~2~bots}, \texttt{ai~-~3~bots}). At a table the
players get ready, and when all are, a countdown starts; then each places
the ships, and the turns begin. Your board, with your ships, is on the
left, the others on the right, or each in a quarter of the screen when
there are three or four. Hits burn, misses splash, and under or beside
each board is that player's fleet, crossed out as it sinks. Between the
boards is whose turn it is. The server gives each player a time to move;
the last twenty seconds count down at the bottom right, and then the
server moves for you.

\begin{keys}[1.1in]
\key{Up}, \key{Down} & In the list of tables, choose one;
\key{Space} joins it. \key{R} lists them again, \key{H} shows how to
play, \key{N} changes your name, \key{S} turns the sound on or off, and
\key{Q} quits.\\
\key{Space} & At a table, get ready, or not.\\
\key{R} & While placing a ship, turn it; the arrows move it, and
\key{Space} places it.\\
\key{A}--\key{J}, \key{1}--\key{0} & On your turn, aim at that column or
row (\key{0} is row 10); the arrows aim too, and \key{Space} fires.\\
\key{Esc} & The menu: \key{Q} leaves the table, \key{H} shows how to
play, \key{S} turns the sound on or off, and \key{Space} goes back.\\
\end{keys}
At the end of a game, \key{Space} goes on to the next.
\rh{Restrictions}
NitrOS-9 waits while the FujiNet fetches each reply from the server,
which takes a second or more. The screen must be at least 80 columns by
24 lines, and show UTF-8. The sounds are played on the SN76489
(\rp{sn76489}{4}).
\rh{Files}
\begin{keys}[1.75in]
\file{/FujiNet/00010100.key} & On the FujiNet's SD card: your name, for
the games of the FujiNet's lobby.\\
\file{/FujiNet/00010105.key} & The server and the table you are at, so
that \cmd{fnbattleship} goes back to it after a reset; leaving the table
forgets it.\\
\file{/FujiNet/e41c0500.key} & Whether the sound is on, and that how to
play has been shown.\\
\end{keys}
\rh{See Also} \rp{fnbounce}{1}, \rp{fujinet}{4}, \rp{sn76489}{4}
\end{refpage}

\refentry{fnbounce}{1}{Bounce World}
\begin{refpage}
\rh{Name} \cmd{fnbounce} -- Bounce World, through the FujiNet
\rh{Syntax} \cmd{fnbounce}
\rh{Description}
The \cmd{fnbounce} command is a client of Bounce World, a world of shapes
that bounce off one another and off its edges. A server keeps the world,
which is made of the screens of all its clients side by side, so that a
shape that leaves one computer's screen comes onto the next one's.
\cmd{fnbounce} starts with its title screen, which shows its version
and the day it was built, and where the server, a name, and the width of
the world are set; the FujiNet keeps them in app keys from one run to the
next. Then it shows the kinds of shape, and then its part of the world,
ten times a second.

\begin{keys}[1in]
\key{S} & Type the server: \var{host}\texttt{:}\var{port}, where the port
is the server's framed TCP port, 9003 unless it was set otherwise;
\texttt{tcp://} is added if it is left out.\\
\key{N} & Type a name, of up to seven characters.\\
\key{W} & Change the world's width between 40 and 80. At 40 each place
of the world is two columns of the terminal, so that the shapes are round;
at 80 a place is a column, and the world is twice as wide, with narrower
shapes.\\
\key{Esc} & Quit.\\
\end{keys}
Any other key goes on. While a setting is typed, \key{Esc}, or typing
nothing, leaves it as it was. In the world:

\begin{keys}[1in]
\key{I} & Show or hide two lines of information: the name, how many
clients there are and how many shapes of each size, the world's size (in
reverse video while it is frozen), and the keys.\\
\key{W} & Show or hide the names of the clients.\\
\key{1}--\key{5} & Add a shape of that size.\\
\key{+}, \key{-} & Speed the world up; slow it down.\\
\key{F} & Freeze the world, or let it go again.\\
\key{R} & Reset the world.\\
\key{C} & Show the screen in reverse video, or not.\\
\key{L} & Flash the screen when shapes collide, or not.\\
\key{S} & Make a sound when shapes collide, or not.\\
\key{Q}, \key{Esc} & Quit. \key{Ctrl/C} is the same.\\
\end{keys}
The world is shared: \key{1}--\key{5}, \key{+}, \key{-}, \key{F}, and
\key{R} change it for every client.
\rh{Restrictions}
The server must be of version 2.3 or later; its other port, 9002, is for
older clients, whose replies have no length, and \cmd{fnbounce} cannot
read them. The screen must be at least 80 columns by 24 lines, and show
UTF-8. The sound is a burst on the noise voice of the SN76489
(\rp{sn76489}{4}).
\rh{Examples}
To use the server at \texttt{bouncy.diller.org}, type \key{S} at the title
screen, then
\begin{exsmall}
bouncy.diller.org:9003
\end{exsmall}
\rh{See Also} \rp{fnnews}{1}, \rp{fnstocks}{1}, \rp{fujinet}{4}
\end{refpage}

\refentry{fnweather}{1}{the weather where you are}
\begin{refpage}
\rh{Name} \cmd{fnweather}, \cmd{fnwx} -- the weather where you are, through the FujiNet
\rh{Syntax} \cmd{fnweather}\\

\rh{Description}
The \cmd{fnweather} command shows the weather where you are, now and for

\refentry{fujinet}{1}{commands for the FujiNet}
\begin{refpage}
\rh{Name} \cmd{fnstatus}, \cmd{fnlisthosts}, \cmd{fngethost},
\cmd{fnsethost}, \cmd{fnmount}, \cmd{fnlistdevs}, \cmd{fngetdevfile},
\cmd{fnsetdevfile}, \cmd{fnmountimg} -- manage the FujiNet
\rh{Syntax} \cmd{fnstatus}\\
\cmd{fnlisthosts}\\
\cmd{fngethost} \var{host\_slot}\\
\cmd{fnsethost} \var{host\_slot} \var{host}\\
\cmd{fnmount} \var{host\_slot}\\
\cmd{fnlistdevs}\\
\cmd{fngetdevfile} \var{device\_slot}\\
\cmd{fnsetdevfile} \var{device\_slot} \var{host\_slot} \var{mode} \var{path}\\
\cmd{fnmountimg} \var{device\_slot} [\var{mode}]
\rh{Description}
These commands talk to the FujiNet through \file{/N1}. A FujiNet has eight
\emph{host slots}, each a place images come from: a TNFS server, or
\texttt{SD} for its own SD card. It has four DriveWire \emph{device
slots}, each an image from a host, which NitrOS-9 sees as the disks
\file{/X0}--\file{/X3}. Slots are numbered from 0, as the FujiNet numbers
them: device slot~0 is \file{/X0}. A \var{mode} is 1 for read-only or 2
for read/write.

\begin{keys}[1.05in]
\cmd{fnstatus} & Print the FujiNet's firmware version, host name, WiFi
network, IP address, gateway, netmask, and name server, and whether the
WiFi is connected.\\
\cmd{fnlisthosts} & List the host slots.\\
\cmd{fngethost} & Print one host slot.\\
\cmd{fnsethost} & Set one host slot, keeping the others.\\
\cmd{fnmount} & Mount a host, so that its images can be used.\\
\cmd{fnlistdevs} & List the device slots: each one's host slot, mode, and
image.\\
\cmd{fngetdevfile} & Print one device slot's image.\\
\cmd{fnsetdevfile} & Put the image \var{path}, from host
\var{host\_slot}, in a device slot. The FujiNet saves it.\\
\cmd{fnmountimg} & Mount a device slot's image (read-only, unless
\var{mode} is 2).\\
\end{keys}
\rh{Examples}
Use an image on the FujiNet's SD card (host slot~1) as \file{/X1}:
\begin{ex}
OS9: \textbf{fnsetdevfile 1 1 2 /games/disk.dsk}
OS9: \textbf{fnmountimg 1 2}
OS9: \textbf{dir /x1}
\end{ex}
\rh{See Also} \rp{fnconfig}{1}, \rp{fujinet}{4}
\end{refpage}

\sans{Memory} & The RAM, what is free (and the largest piece that is

\sans{Processes} & Every process: its number, its parent, its user, its

\sans{Devices} & Every device descriptor in memory, with its file manager,

\sans{Disks} & Each disk drive (once, though several descriptors may name

\sans{Interrupts} & The entries in the IRQ polling table, with the driver

\sans{Modules} & The names of the modules in memory, and their total size.\\
\sans{Hardware} & The TFR/911H firmware's own report: the board, the

\end{keys}

the memory map in it to copy what it needs with \texttt{F\$CpyMem}. The
hardware report comes from the firmware's info port; see \rp{tfr911h}{4}.
\rh{Options}
\begin{keys}[0.5in]
\texttt{-p} & Plain text: leave out the escape sequences that make the
headings bold, for saving the report to a file.\\
\end{keys}
\rh{Restrictions}

chip's temperature is shown only when its reading is believable.

On firmware without the info port, the hardware part says so and is
otherwise empty.

\refentry{tsh}{1}{the shell, with line editing}
\begin{refpage}
\rh{Name} \cmd{tsh} -- the shell, with line editing, history, completion,
and a search path
\rh{Syntax} \cmd{tsh} [\var{file}]
\rh{Description}
\cmd{tsh} is the shell you type to after booting: the last line of
\file{startup} starts it. It reads each line itself, so that you can move
about in the line and change it, call back the lines you typed before,
and have names finished with \key{Tab}. Then it hands the line to the
OS-9 Shell to run. So commands are written as for the Shell: \texttt{!}
for a pipe, \texttt{<}, \texttt{>}, \texttt{>>} and the rest for
redirection, \texttt{\#}\var{n}\texttt{K} for memory, \texttt{\&} and
\texttt{;}, parentheses, and procedure files all work as they always
have.

A command that is neither in memory nor in the execution directory is
looked for in each directory of the \emph{path} in turn; see \cmd{path}
below. \file{/DD/SYS/tshrc} sets it when \cmd{tsh} starts.

\type{exit} leaves \cmd{tsh}. After booting, that gives the OS-9 Shell;
type \type{tsh} to come back. Given a \var{file}, \cmd{tsh} runs the
commands in it and exits; and if its standard input is not a terminal,
it runs the commands it reads there.

\sans{\textbf{Editing}}
\begin{keys}[1.5in]
\key{Left} \key{Right}, \texttt{\^{}B} \texttt{\^{}F} & Move a character.\\
\texttt{\^{}A} \texttt{\^{}E} & To the start or the end of the line.\\
\key{Esc} \texttt{b}, \key{Esc} \texttt{f} & Back or on a word.\\
\key{Backspace} & Delete the character before the cursor.\\
\texttt{\^{}D} & Delete the character under the cursor.\\
\texttt{\^{}W} & Delete back to a space: the word before the cursor.\\
\key{Esc} \key{Backspace}, \key{Esc} \texttt{d} & Delete a word back, or
on.\\
\texttt{\^{}K} \texttt{\^{}U} & Delete to the end of the line, or to its
start.\\
\texttt{\^{}X} & Delete the whole line.\\
\texttt{\^{}Y} & Put back what was deleted last.\\
\texttt{\^{}T} & Swap the two characters before the cursor.\\
\texttt{\^{}L} & Clear the screen and draw the line again.\\
\texttt{\^{}C} & Give up the line.\\
\key{Return} & Run it, wherever the cursor is.\\
\end{keys}
A line longer than the screen scrolls sideways; a \texttt{<} at its left
or a \texttt{>} at its right shows that there is more.

\sans{\textbf{History}}
\begin{keys}[1.5in]
\key{Up} \key{Down}, \texttt{\^{}P} \texttt{\^{}N} & The line before, or
after.\\
\key{Shift/Up} \key{Shift/Down} & The line before, or after, that starts
as this one does, up to the cursor: type \type{cop} and press
\key{Shift/Up} for the last \cmd{copy}.\\
\texttt{\^{}R} & Search back: type some of the line you want, and
\texttt{\^{}R} again for an older one. \key{Return} runs it; any other key
leaves it to be edited; \texttt{\^{}C} gives up.\\
\end{keys}
The last 100 lines are kept in \file{/DD/SYS/tsh\_history}, so they are
there after booting again. \cmd{tsh} adds them to the file ten at a time,
and when it exits; quitting the tether loses none, since \cmd{tsh} goes on
running on the board, but pressing \key{RESET} loses those not yet
written.

\sans{\textbf{Completion}}
\key{Tab} finishes the word before the cursor. At the start of a command
it is a command's name: built in, an alias, or a file in the execution
directory or a directory of the path. Anywhere else it is a file's name,
in the data directory or in the directory the word gives. A directory is
followed by \texttt{/}, anything else by a space. When several names
fit, \key{Tab} adds what they begin with in common, and a second
\key{Tab} lists them.

\sans{\textbf{Built-in commands}}
\begin{keys}[1.5in]
\cmd{cd} [\var{dir} \(|\) \texttt{-}], \cmd{chd} & Change the data
directory: to \file{/DD} without one, back to the last with \texttt{-}.\\
\cmd{chx} \var{dir} & Change the execution directory.\\
\cmd{path} [\var{dir} \ldots] & Show the path, or set it.
\texttt{+}\var{dir} adds a directory at the end, \texttt{-}\var{dir} takes
one out, \texttt{-} empties it. A relative \var{dir} is made full from the
data directory.\\
\texttt{PATH=}\var{dir}\texttt{:}\var{dir} & Set the path (spaces
separate them too).\\
\texttt{PROMPT=}\var{text} & Set the prompt (\texttt{OS9:} to begin
with): \texttt{\%d} is the data directory, \texttt{\%w} the last name in
it, \texttt{\%h} the number the next line will have in the history,
\texttt{\%e} the last command's exit status, \texttt{\%t} the time.\\
\texttt{COLS=}\var{n} & The screen's width (80).\\
\cmd{set} & Show \texttt{PATH}, \texttt{PROMPT}, and \texttt{COLS}.\\
\cmd{history} [\var{n} \(|\) \texttt{-c}] & List the history, or the
last \var{n} lines of it; \texttt{-c} forgets it all.\\
\cmd{alias} [\var{name} [\var{text}]] & Make \var{name}, as the first word
of a command, stand for \var{text}. With only a name, show it; with
nothing, list them all. \cmd{unalias} \var{name} removes one.\\
\cmd{source} \var{file}, \cmd{.} & Run the commands in \var{file} in this
\cmd{tsh}.\\
\cmd{which} \var{name} \ldots & Say what each name is: an alias, built in,
in memory, in the execution directory, or where on the path.\\
\cmd{w}, \cmd{wait} & Wait for the commands in the background to
finish.\\
\cmd{kill}, \cmd{setpr} & As in the Shell.\\
\cmd{x} \cmd{-x}, \cmd{p} \cmd{-p}, \cmd{t} \cmd{-t} & As in the Shell:
stop at an error, show no prompt, echo each line; or not.\\
\cmd{ex} \var{command} & Run \var{command}, then leave \cmd{tsh}.\\
\cmd{exit} [\var{status}] & Leave \cmd{tsh}.\\
\texttt{*} & A comment, to the end of the line.\\
\end{keys}

\sans{\textbf{How it runs a command}} For each command between
\texttt{;} and \texttt{\&}, \cmd{tsh} puts an alias's text in place of
its name, does a built-in command itself, and starts \texttt{Shell}
\var{command} for any other, waiting for it unless \texttt{\&} followed.
The Shell's own built-in commands are done by \cmd{tsh}, because a Shell
given only \type{chd /dd} would change its own directory, not
\cmd{tsh}'s, and then wait for more input. A command name found on the
path is loaded by \cmd{tsh} with \texttt{F\$Load}, so the Shell finds it
in memory, and unlinked when the command has finished. A procedure file
on the path is given to the Shell as a full pathlist.

\cmd{tsh} reads keys through a path of its own to the terminal, with echo,
paging, and the keyboard's signals turned off for that path alone, so the
Shell and other programs see the terminal as they always have. On the
TFR/911H's console it sets bit~7 of \file{\$FF42} while you edit a line,
for the arrow keys (see \rp{tfr911h}{4}), and clears it before running the
line. It draws with backspaces, carriage returns, and printing
characters, so any terminal will do; \texttt{\^{}L} alone sends ANSI
sequences.

\key{Ctrl/C} and \key{Ctrl/E} reach a running command as they always
have. If the command has not used the terminal since \cmd{tsh} did, they
come to \cmd{tsh} instead, and it aborts the command with \texttt{S\$Abort},
through its Shell.
\rh{Restrictions}
The tether passes on the arrow keys, and Shift with the up and down
arrows, but not \key{Home}, \key{End}, or \key{Delete}: use
\texttt{\^{}A}, \texttt{\^{}E}, and \texttt{\^{}D}. Over a network, from a
terminal that sends them as ANSI sequences, those keys work too.

There are no variables but \texttt{PATH}, \texttt{PROMPT}, and
\texttt{COLS}, and no wildcards: the Shell has none either. A line is at
most 250 characters. Each command costs a process for its Shell, about
8K of memory while it runs. The Shell's \texttt{i=} is not taken.
\rh{Examples}
Find out where commands come from, and add a directory to the path:
\begin{ex}
OS9:\textbf{which dir ll fnweather}
dir: in the execution directory
ll: in the execution directory
fnweather: in the execution directory
OS9:\textbf{path +/H0/BIN}
OS9:\textbf{path}
/DD/CMDS /H0/CMDS /H0/BIN
\end{ex}
An alias, and a prompt that shows the directory:
\begin{ex}
OS9:\textbf{alias lsl dir -e}
OS9:\textbf{lsl ! more}
OS9:\textbf{PROMPT="\%d: "}
/DD: \textbf{cd cmds}
/DD/CMDS:
\end{ex}

\file{/DD/SYS/tsh\_history} & The history.\\
\file{/DD/startup} & Ends with \type{tsh </term}, to start it after

\refentry{unix}{1}{Unix-style names for OS-9 commands}
\begin{refpage}
\rh{Name} \cmd{unix} -- Unix-style names for OS-9 commands
\rh{Syntax} \cmd{ls} [\texttt{-l}] [\var{path}]\quad \cmd{cd} \var{path}\quad \cmd{cat} \var{path}\quad \ldots
\rh{Description}
The TFR/911H's NitrOS-9 knows the names a Unix user reaches for first. Most
are \emph{aliases}: tiny modules that run the OS-9 command that does the
job, passing along their arguments. Two are built into the Shell and
\cmd{tsh}, and the rest are real commands. \type{man unix} on the board lists them.

\begin{tabularx}{\linewidth}{@{}l l X@{}}
\toprule
\textbf{Name} & \textbf{Runs} & \textbf{What it does}\\
\midrule
\cmd{ls} [\texttt{-l}] & \cmd{dir} [\texttt{-e}] & List a directory; \texttt{-l} gives the long form\\
\cmd{ll} & \cmd{dir -e} & List a directory, long form\\
\cmd{cat} & \cmd{list} & Print a text file\\
\cmd{cp} & \cmd{copy} & Copy a file\\
\cmd{mv} & \cmd{rename} & Rename a file or directory\\
\cmd{rm} & \cmd{del} & Delete files\\
\cmd{mkdir} & \cmd{makdir} & Make a directory\\
\cmd{rmdir} & \cmd{deldir} & Delete a directory and what is in it\\
\cmd{ps} & \cmd{procs} & List processes; \texttt{-e} lists everyone's\\
\cmd{df} & \cmd{free} & Show free space on a disk\\
\cmd{less} & \cmd{more} & Show a file a screen at a time\\
\cmd{man} & \cmd{help} & Show help for a command\\
\cmd{uname} & \cmd{echo} & Say what this is\\
\cmd{vim} & \cmd{vi} & The editor; see \rp{vi}{1}\\
\midrule

An alias puts any extra arguments of its own in front of yours, and then
chains to the real command with \texttt{F\$Chain}, so it costs no extra
process. \cmd{cd} and \cmd{exit} are added to the table of built-in
commands in a copy of the Shell's source.
\rh{Restrictions}
These are OS-9 commands under Unix names, and they behave as OS-9
commands. \cmd{mv} cannot move a file to another directory. \cmd{rmdir}
deletes the directory's contents too, after asking. \cmd{rm} takes no
options.

The Shell's syntax is OS-9's, not the Bourne shell's: the pipe symbol is
\texttt{!}, \texttt{>>} redirects standard error (there is no append),
\texttt{<>} and \texttt{>>>} redirect several paths at once, and
\texttt{\&} runs a command in the background.

\begin{ex}

OS9:\textbf{cp notes /dd/src/notes}
OS9:\textbf{cd /dd/src}
OS9:\textbf{ps}
\end{ex}

\refentry{vi}{1}{a small vi}
\begin{refpage}
\rh{Name} \cmd{vi}, \cmd{vim} -- a small vi
\rh{Syntax} \cmd{vi} [\texttt{-w} \var{cols}] [\texttt{-h} \var{rows}] [\var{file}]
\rh{Description}
The \cmd{vi} command is a screen editor in the manner of the Unix
\cmd{vi}, with most of the commands people use without thinking about
them. It starts in \emph{normal} mode, where keys are commands. The
insert commands enter \emph{insert} mode, where keys are text, until you
press \key{Esc}. A colon starts a \emph{command line} at the bottom of the
screen.

The bottom line shows messages, \texttt{-- INSERT --} in insert mode, and
the cursor's line and column. Lines longer than the screen are not wrapped:
the view scrolls sideways.

Most normal-mode commands take a count in front: \type{3dd} deletes three
lines, \type{5j} moves down five, \type{2d3w} deletes six words.

\sans{\textbf{Moving}}
\begin{keys}
\texttt{h j k l} & Left, down, up, right. The arrow keys too.\\
\texttt{w b e} & To the next word, back a word, to the end of the word.
\texttt{W B E} do the same with words that are anything but blanks.\\
\texttt{0 \^{} \$} & To the start of the line, its first non-blank, its end.\\
\texttt{G}, \texttt{gg} & To the last line, or to line \var{n} with a count;
to the first line.\\
\texttt{H M L} & To the top, middle, or bottom of the screen.\\
\texttt{f}\var{c} \texttt{F}\var{c} \texttt{t}\var{c} \texttt{T}\var{c} & To the next
(\texttt{f}) or previous (\texttt{F}) \var{c} on the line, or just before it
(\texttt{t}, \texttt{T}). \texttt{;} repeats; \texttt{,} repeats the other way.\\
\texttt{\%} & To the bracket that matches the next \texttt{( [ \{ \} ] )}.\\
\texttt{\{ \}} & Back or on a paragraph (to a blank line).\\
\texttt{+ - Return} & Down or up a line, to its first non-blank.\\
\texttt{\^{}F \^{}B} & Forward or back a screen. Page Down and Page Up too.\\
\texttt{\^{}D \^{}U} & Down or up half a screen.\\
\end{keys}

\sans{\textbf{Searching}}
\begin{keys}
\texttt{/}\var{text}, \texttt{?}\var{text} & Find \var{text} forward or backward,
wrapping around the file.\\
\texttt{n N} & Find it again, the same way or the other.\\
\texttt{*} & Find the word under the cursor.\\
\end{keys}

\sans{\textbf{Inserting}}
\begin{keys}
\texttt{i a} & Insert before, or append after, the cursor.\\
\texttt{I A} & Insert at the line's first non-blank, or append at its end.\\
\texttt{o O} & Open a new line below, or above.\\
\end{keys}
In insert mode, \key{Backspace} deletes the character before the cursor
(and can join lines), \texttt{\^{}W} the word before it, \texttt{\^{}U} the line
before it; \key{Return} splits the line, \key{Tab} inserts a tab, and the
arrow keys move the cursor. \key{Esc} goes back to normal mode.

\sans{\textbf{Changing}}
\begin{keys}
\texttt{x X} & Delete the character under, or before, the cursor.\\
\texttt{D C} & Delete, or change, to the end of the line.\\
\texttt{s S} & Change a character, or the whole line.\\
\texttt{r}\var{c} & Replace the character with \var{c} (\texttt{r} \key{Return} splits the line).\\
\texttt{J} & Join this line and the next.\\
\texttt{\~{}} & Switch the case of the character, and move on.\\
\texttt{>> <<} & Indent the line by a tab, or take one away.\\
\texttt{p P} & Put the last deleted or yanked text after, or before, the cursor
(below or above, for whole lines).\\
\texttt{u} & Undo the last change. Again and again, back to the start.\\
\texttt{.} & Do the last change again.\\
\end{keys}

\sans{\textbf{Operators}} \texttt{d} (delete), \texttt{c} (change),
\texttt{y} (yank), \texttt{>} and \texttt{<} (indent) work on the text that
any motion moves over: \type{dw}, \type{c\$}, \type{y3j}, \type{dG},
\type{d/end}, \type{>\}}. Doubled, they work on whole lines: \type{dd},
\type{cc}, \type{yy}, \type{>>}. \texttt{Y} is \texttt{yy}.

\sans{\textbf{Other}}
\begin{keys}
\texttt{ZZ} & Write the file if it was changed, and quit.\\
\texttt{ZQ} & Quit without writing.\\
\texttt{\^{}G} & Show the file's name, length, and where you are in it.\\
\texttt{\^{}L} & Redraw the screen.\\
\end{keys}

\sans{\textbf{Command line}}
\begin{keys}[1.75in]
\texttt{:w} [\var{file}] & Write the file, or write to \var{file}.\\
\texttt{:q}, \texttt{:q!} & Quit; \texttt{!} quits even if there are unsaved changes.\\
\texttt{:wq}, \texttt{:x} & Write and quit (\texttt{:x} writes only if there were changes).\\
\texttt{:e}[\texttt{!}] [\var{file}] & Edit another file, or the same file again.\\
\texttt{:r} \var{file} & Read \var{file} in below the current line.\\
\texttt{:}\var{n}, \texttt{:\$} & Go to line \var{n}, or the last line.\\
\texttt{:}[\var{range}]\texttt{s/}\var{old}\texttt{/}\var{new}\texttt{/}[\texttt{g}] &
Replace \var{old} with \var{new}, once in each line or everywhere

\texttt{:help} & A reminder of these.\\
\end{keys}
A \var{range} is a line number, \texttt{.} (this line), \texttt{\$} (the
last), two of them with a comma (\texttt{2,10}), or \texttt{\%} (every
line). Without one, a command works on the current line.

\begin{keys}[0.8in]
\texttt{-w} \var{cols} & The terminal's width (default 80).\\
\texttt{-h} \var{rows} & The terminal's height (default 24).\\

\rh{Restrictions}
Searches are for plain text, not regular expressions. There is one
register, there are no marks, no visual mode, no \texttt{:set}, and no
redo. The text must fit in memory: about 25K. Undo remembers as many
changes as fit in its own space, and forgets the oldest first.

OS-9 text files end their lines with a carriage return. \cmd{vi} reads
files that end them with CR, LF, or CR~LF, and writes CR.

The arrow keys work in insert mode because \cmd{vi} sets bit~7 of
\file{\$FF42} while it runs, so that the firmware sends them untranslated
(see \rp{tfr911h}{4}). If \cmd{vi} is killed, they stay that way until
the next \cmd{vi} ends.

\begin{ex}

\textbf{:wq}
\end{ex}

\begin{ex}
\textbf{d/end}
\textbf{u}
\end{ex}

\refentry{fujinet}{4}{the FujiNet}
\begin{refpage}
\rh{Name} \cmd{fujinet} -- the FujiNet, its disks, and booting from it
\rh{Description}
A FujiNet is a network adapter for old computers: an ESP32 with WiFi and
an SD card. On the TFR/911H it runs the FujiNet firmware for the Color
Computer, built for the board \texttt{fujinet-coco-devkitc-centipede},
which speaks DriveWire over a 3.3-volt serial link at 921{,}600 baud. It is

\midrule

GND & GND & \\
\bottomrule
\end{tabularx}

\sans{\textbf{The becker port}}\quad The firmware passes the link to the
6309 as a becker port, the kind CoCo emulators give DriveWire:

\begin{keys}[1.05in]
\file{\$FF45} & Read: bit~1 is set when a byte from the FujiNet is
waiting.\\
\file{\$FF46} & Read: the next byte from the FujiNet. Write: a byte to
the FujiNet.\\
\end{keys}
Emulators have the becker port at \file{\$FF41}, where the TFR/911H has its
sound chip, so NitrOS-9's DriveWire modules are built with
\texttt{BECKBASE} set to \file{\$FF45}. The firmware keeps 4K of what the
FujiNet sends, so nothing is lost while the 6309 is busy.

\sans{\textbf{Devices}}\quad \file{/X0}--\file{/X3} are the FujiNet's four
device slots, as DriveWire disks (\file{rbdw}). \file{/N} and
\file{/N1}--\file{/N5} are DriveWire's network devices (\file{scdwv}); the
\rp{fujinet}{1} commands use \file{/N1}, and its \texttt{SS.Fuji} SetStat,
which sends a request to the FujiNet and reads its reply with interrupts
masked. There is no virtual-serial poller, which would take the
FujiNet's replies for itself.

\sans{\textbf{Booting from the FujiNet}}\quad At the \texttt{TCL>} prompt,
\cmd{l2fn} mounts the image in the FujiNet's first device slot (slot~0),
and boots NitrOS-9 from it: the kernel is in the firmware, as for \cmd{l2},
and its \file{Boot} module loads \file{OS9Boot} from DriveWire drive~0.
That \file{OS9Boot} makes \file{/X0} the system disk, \file{/DD}; the
tether's disk is \file{/H0}. To make such a disk, put it on the FujiNet,
and boot it:
\begin{ex}
$ \textbf{cd v4/nitros9-l2}
$ \textbf{make fujinet-disk}
$ \textbf{curl -X MKCOL http://\var{fujinet}/dav/tfr911}
$ \textbf{curl -T level2-fn.dsk http://\var{fujinet}/dav/tfr911/level2-fn.dsk}
\end{ex}
Then, with NitrOS-9 booted with \cmd{l2}, put the image in device slot~0
(host slot~1 being the SD card), and boot it:
\begin{ex}
OS9: \textbf{fnsetdevfile 0 1 2 /tfr911/level2-fn.dsk}
\end{ex}
\begin{ex}
$ \textbf{BOOT=l2fn sh run-l2.sh}
\end{ex}
\cmd{make fujinet-disk} copies \file{level2.dsk}, with your files, to
\file{level2-fn.dsk}, and gives the copy the FujiNet's \file{OS9Boot}.
The FujiNet's web server offers its SD card by WebDAV at \file{/dav}.
Chapter~2 describes the FujiNet, the link, and programming it at length.
\rh{Restrictions}
At power on, the FujiNet puts its own CONFIG disk in device slot~0; that
is why \cmd{l2fn} mounts the slot first.

The FujiNet keeps the image file open. After replacing the file, mount it
again (\cmd{l2fn} does, as does \texttt{fujinet mount 1} at
\texttt{TCL>}).

\texttt{OP\_DWINIT}; firmware that does not loses the command after it, and
the 6309 waits for ever. See \file{v4/nitros9-l2/fujinet/README.md}.

\refentry{sn76489}{4}{the sound chip}
\begin{refpage}
\rh{Name} \cmd{sn76489} -- the sound chip
\rh{Syntax} \file{\$FF41}, write only
\rh{Description}
The TFR/911H firmware emulates a Texas Instruments SN76489 sound
generator at \file{\$FF41}, the address of the one in the Color Computer's
Game Master Cartridge. It has three square-wave tone voices and a noise
voice, each with sixteen volumes. The firmware mixes them at 31,250
samples a second, with the keyclick and bell sounds, and plays the result
as pulse-width-modulated audio on GPIO~8 (see Appendix~A).

The chip is programmed one byte at a time. A byte with bit~7 set
\emph{latches} a voice and a register and gives the low four bits of the
value; a byte with bit~7 clear gives the high six bits of a tone's period:

\begin{tabularx}{\linewidth}{@{}l X@{}}
\toprule
\textbf{Byte} & \textbf{Meaning}\\
\midrule
\texttt{1 vv 0 dddd} & Voice \texttt{vv} (0--2): low 4 bits of its period\\
\texttt{0 0 dddddd} & The high 6 bits of the latched voice's period\\
\texttt{1 vv 1 aaaa} & Voice \texttt{vv} (0--3): attenuation, 2~dB a step;
\texttt{1111} is off\\
\texttt{1 11 0 0 f rr} & The noise voice: \texttt{f}=1 white noise, 0
periodic; \texttt{rr} its rate, 0--2, or 3 to follow voice~2\\
\bottomrule
\end{tabularx}

A tone's period \var{N} (1--1023) gives a frequency of
3,579,545\,/\,(32\,×\,\var{N})~Hz, so A440 is \var{N}~=~254, and the
lowest note is about 109~Hz.

The control register at \file{\$FF42} is read and write:
\begin{keys}[0.6in]
bit 0 & Keyclicks on (see \rp{click}{1}).\\
bit 1 & The bell sounds on \texttt{\^{}G} (see \rp{beep}{1}).\\
bit 7 & Arrow keys untranslated (see \rp{tfr911h}{4}).\\
\end{keys}
\rh{Examples}
In C, compiled with CMOC, from \rp{tetris}{6}:
\begin{ex}
#define SND (*(volatile unsigned char *)0xFF41)

void note(unsigned char voice, unsigned n) \{   /* n = 3579545/32/Hz */
    SND = 0x80 | (voice << 5) | (n & 15);
    SND = (n >> 4) & 0x3F;
\}

void volume(unsigned char voice, unsigned char att) \{ /* 15 is off */
    SND = 0x90 | (voice << 5) | att;
\}
\end{ex}
\rh{See Also} \rp{beep}{1}, \rp{click}{1}, \rp{tfr911h}{4}, Appendix~A
\end{refpage}

\refentry{tfr911h}{4}{the hardware the firmware emulates}
\begin{refpage}
\rh{Name} \cmd{tfr911h} -- the hardware the TFR/911H firmware emulates for NitrOS-9 Level 2
\rh{Description}
To NitrOS-9, the TFR/911H is a small Color Computer~3. The firmware's
second core answers every bus cycle of the 6309: reads and writes of RAM
go to the RP2350B's memory through the emulated MMU, and those of the I/O
page, \file{\$FF00}--\file{\$FFFF}, go to the devices below. Locations not
listed read back what was last written to them. The 6309 runs in 6809
mode.

\sans{\textbf{Memory}}\quad 256K of RAM, in 32 blocks of 8K. The GIME's MMU
maps eight blocks into each of two tasks' 64K address spaces:
\file{\$FFA0}--\file{\$FFA7} for task~0 and \file{\$FFA8}--\file{\$FFAF}
for task~1. \file{\$FF90} bit~6 enables the MMU and bit~5 the GIME's
interrupts; \file{\$FF91} bit~0 picks the task. \file{\$FE00}--\file{\$FEFF}
is the constant page, the same in every map.

\sans{\textbf{Interrupts}}\quad \file{\$FF92} bit~3 enables the vertical
border (VBORD) interrupt, which a timer in the firmware raises 60 times a
second; reading \file{\$FF92} acknowledges it. The 6850's interrupt joins
it on the 6309's IRQ line. There is no FIRQ.

\sans{\textbf{Console}}\quad An MC6850 ACIA at \file{\$FF14} (status and
control) and \file{\$FF15} (data). Its transmitter is always ready;
characters go to the tether at once.

\sans{\textbf{Disk}}\quad EmuDsk, a virtual hard disk whose sectors the
tether reads and writes in a file:
\begin{keys}[1.05in]
\file{\$FF80}--\file{\$FF82} & The logical sector number, 24 bits.\\
\file{\$FF83} & Write a command: 0 reads a sector, 1 writes one. Read the
status: 0 if it worked.\\
\file{\$FF84}--\file{\$FF85} & The address of the 256-byte buffer.\\
\file{\$FF86} & The drive number.\\
\end{keys}
The bus waits while the tether moves the sector over USB, so the status is
ready in the instruction after the command.

\sans{\textbf{Clock}}\quad \file{\$FFC0}--\file{\$FFC7} hold the century,
year, month, day, day of the week, hour, minute, and second, in binary,
in the format of Jeff Vavasour's CoCo~3 emulator. The tether sends your
computer's local time when it connects, and the firmware keeps it going.

\sans{\textbf{Sound}}\quad \file{\$FF41} and \file{\$FF42}; see \rp{sn76489}{4}.

\sans{\textbf{FujiNet}}\quad A becker port at \file{\$FF45} (status) and
\file{\$FF46} (data), for DriveWire to a FujiNet; see \rp{fujinet}{4}.

\sans{\textbf{Info port}}\quad The firmware's report on itself, for
\rp{info}{1}. Write \file{\$A5} to \file{\$FF43}; when \file{\$FF43} reads
1, each read of \file{\$FF44} gives the report's next character, and 0
after the last. The report is lines of the form
\var{label}~\texttt{TAB}~\var{value}~\texttt{LF}.

\sans{\textbf{Keyboard}}\quad Keys typed in the tether reach OS-9 through the
6850. The tether turns Delete into Backspace and Enter into a carriage
return. The arrow keys arrive as a Color Computer~3 sends them, unless
bit~7 of \file{\$FF42} is set:

\begin{tabularx}{\linewidth}{@{}l l l X@{}}
\toprule
\textbf{Key} & \textbf{CoCo code} & \textbf{Bit 7 set} & \textbf{Note}\\
\midrule
Up & \file{\$0C} & 128 & \\
Down & \file{\$0A} & 129 & \\
Left & \file{\$08} & 130 & The same as Backspace, as CoCo code\\
Right & \file{\$09} & 131 & The same as Tab, as CoCo code\\
Page Up & --- & 132 & Dropped, as CoCo code\\
Page Down & --- & 133 & Dropped, as CoCo code\\
\bottomrule
\end{tabularx}
\rh{Files}
\begin{keys}[2.2in]
\file{v4/tfr911h/v4\_nitros9\_l2.h} & The emulation.\\
\file{v4/tfr911h/v4\_audio.h} & The sound chip and the mixer.\\
\file{v4/tfr911h/v4\_fujinet.h} & The becker port.\\
\end{keys}
\rh{See Also} \rp{info}{1}, \rp{fujinet}{4}, \rp{sn76489}{4}, \rp{tether}{8}
\end{refpage}

\refentry{tetris}{6}{Tetris, with music}
\begin{refpage}
\rh{Name} \cmd{tetris} -- Tetris, with music
\rh{Syntax} \cmd{tetris}
\rh{Description}
Pieces fall into a well ten cells wide and twenty deep. Move and turn them
so they make full rows, which disappear. The game draws in color on the

\begin{keys}[1.4in]

\key{Up}, \texttt{w} & Turn it.\\

pieces fall faster, up to level~19.

With a speaker connected, the game plays \emph{Korobeiniki} on the sound

\refentry{zm}{6}{a Z-machine, for Infocom's games}
\begin{refpage}
\rh{Name} \cmd{zm} -- play Infocom's games, and others written for the Z-machine
\rh{Syntax} \cmd{zm} [\texttt{-w} \var{cols}] [\texttt{-h} \var{rows}] [\texttt{-m} \var{kbytes}] [\texttt{-d}] \var{story}
\rh{Description}
Infocom wrote its games for an imaginary computer, the Z-machine, and sold
them with an interpreter for each real one. \cmd{zm} is a Z-machine
interpreter for OS-9. It plays \emph{version~3} story files: most of
Infocom's games from 1980 to 1987 (Zork I--III, The Hitchhiker's Guide to
the Galaxy, Planetfall, Enchanter, Deadline, and many more), and games
written with Inform and compiled with \texttt{-v3}.

\cmd{zm} looks for \var{story}, then \var{story}\texttt{.z3}, and, if the
name has no directory in it, the same in \file{/DD/GAMES}. So \type{zm
zork1} finds \file{/DD/GAMES/zork1.z3}.

The top line of the screen is the status line: where you are, and your
score and moves, or the time in the games that keep it. The text scrolls
beneath it, word-wrapped to the screen's width, and pauses with
\texttt{[MORE]} when a screen goes by without your typing. Games that
split the screen, as Seastalker does, can.

The game's commands \texttt{save} and \texttt{restore} ask for a file name,
offering the story's name with \texttt{.sav}; save files go in the data
directory. \texttt{restart}, \texttt{verify}, and \texttt{quit} work as in
the games' manuals.

The part of the story the game can change, its \emph{dynamic memory}, is
kept in RAM. So is as much of the rest as fits---about 40K, got by growing
the process's data area with \texttt{F\$Mem}. If the story is bigger than
that, the rest is read from the file in 512-byte pages as the game needs
them, and the least recently used page gives way. Panic, which is 37K, is
held in memory whole; Zork~I, at 87K, is paged, and still answers a
command in under a second.
\rh{Options}
\begin{keys}[0.8in]
\texttt{-w} \var{cols} & The terminal's width (default 80).\\
\texttt{-h} \var{rows} & The terminal's height (default 24).\\
\texttt{-m} \var{kbytes} & Use at most this much memory for the story
(8--60).\\
\texttt{-d} & A dumb terminal: no status line, no escape sequences, no
\texttt{[MORE]}.\\
\end{keys}
\rh{Restrictions}
Only version~3 stories are played; \cmd{zm} says which version a story is
if it is another. There is no transcript (\texttt{script}), and there are
no sounds but the two beeps of The Lurking Horror, which it plays on the
sound chip.
\rh{Diagnostics}
If the story does something impossible, \cmd{zm} stops with a message
such as:
\begin{ex}
*** zm: stack underflow (PC $1A2B3) ***
\end{ex}
\rh{Examples}
\begin{ex}
OS9:\textbf{zm zork1}
ZORK I: The Great Underground Empire
...
West of House
You are standing in an open field west of a white house, with a boarded
front door.
There is a small mailbox here.

>\textbf{open mailbox}
\end{ex}
To put story files on the disk, see \rp{nitros9-l2}{8}.
\rh{Files}
\begin{keys}[1.6in]

\var{story}\file{.sav} & Saved games.\\
\end{keys}

\refentry{tether}{8}{the board's terminal, disk, and clock}
\begin{refpage}
\rh{Name} \cmd{tether}, \cmd{run-l2.sh} -- the board's terminal, disk, and clock
\rh{Syntax} \cmd{sh run-l2.sh}\\

\rh{Description}
The tether is a program on your computer that talks to the TFR/911H over
USB. It is the board's terminal: what you type goes to the 6309, and what

clock when it connects.

\file{v4/run-l2.sh} builds the tether and runs it with the options
NitrOS-9 Level 2 needs. If NitrOS-9 is already running on the board, it
simply reconnects.

\end{keys}

\begin{keys}[1.25in]

\chapter{Connecting a Speaker}
\chapterpages
\renewcommand{\thesectname}{Connecting a Speaker}

The TFR/911H makes sound as pulse-width-modulated audio on GPIO~8 of the
RP2350B: an 8-bit level carried at about 977~kHz, far above hearing. A
filter and a small amplifier turn it into sound. The firmware was written
for an Adafruit PAM8302, a 2.5~W class~D amplifier on a small board.

\section{Wiring}

GPIO~8 is pin~1 of the 2-by-10 header J3, and is not connected to the
6309. Wire the PAM8302 like this:

\begin{tabularx}{\linewidth}{@{}l l X@{}}
\toprule
\textbf{J3 pin} & \textbf{Signal} & \textbf{PAM8302}\\
\midrule
2 & VBUS (5~V) & Vin\\
6 & GND & GND, and A−\\
1 & GPIO 8 & A+, through a 1~kΩ resistor, with a 10~nF capacitor from A+ to GND\\
\bottomrule
\end{tabularx}

The resistor and capacitor make a low-pass filter that takes out the
carrier. Connect the speaker to the PAM8302's + and − terminals, and
turn its volume control down before you start.

\section{Trying It}

At the \texttt{TCL>} prompt, before an OS is booted:
\begin{ex}
TCL> \textbf{beep 440 1000}
\end{ex}
should play an A for a second. Then, in NitrOS-9, \cmd{beep} rings the
bell, every key clicks (\cmd{click off} stops that), and \cmd{tetris}
plays music.

\section{How It Works}

A timer interrupt on the RP2350B's first core runs 31,250 times a second.
Each time, it takes any bytes the 6309 has written to the SN76489, works
out the next sample of the three tone voices, the noise voice, and the
keyclick or bell, adds them, and sets the PWM level. The 6309's writes
reach it through a queue, so the core that runs the bus never waits.

\chapter{How the Software Was Tested}
\chapterpages
\renewcommand{\thesectname}{How the Software Was Tested}

The C programs were written so that the same source builds for OS-9 with
CMOC and for a Unix computer with an ordinary C compiler. That let each one
be tested against a reference on the big computer, and then on the board.

\section{zm}

\begin{itemize}\setlength{\itemsep}{0.3ex}
\item CZECH, the Comprehensive Z-machine Emulation Checker, compiled for
version~3 with Inform: all 349 of its tests pass, on the Unix build and on
the TFR/911H's 6309, where the run takes about five seconds. They pass
too with memory cut to 8K, which makes nearly every read a page from the
file.
\item Zork I, II, and III and Inform's Adventure: transcripts of
the same commands give the same text, word for word, as \cmd{dfrotz}, a
widely used interpreter, with the story wholly in memory and with only
16K to 40K for it.
\item On the board: Zork~I answers each command in 0.4 to 0.9 seconds;
\texttt{save}, \texttt{restore}, \texttt{restart} work.
\end{itemize}

\section{vi}

\begin{itemize}\setlength{\itemsep}{0.3ex}
\item 123 editing commands---motions, operators, counts, undo,
\texttt{.}, searches, \texttt{:s} and ranges---were typed into Vim and
into \cmd{vi}, on a pseudo-terminal at the same pace, and the files they
wrote compared: all the same.
\item 27 sessions on a 300-line file with tabs and long lines checked that
what \cmd{vi} shows is what is in the file, after scrolling, sideways
scrolling, and edits.
\item On the board: moving and typing answer in under 0.05 seconds,
scrolling in 0.15, and replacing 178 strings on 116 lines in 1.8.
\end{itemize}

\section{tsh}

\begin{itemize}\setlength{\itemsep}{0.3ex}
\item Built for the Unix computer, \cmd{tsh} was driven through a
pseudo-terminal and the screen read back with a terminal emulator: 68
checks of the editing keys, the history keys and the history file,
completion of commands and files, sideways scrolling at 80 and 120
columns, the path, \cmd{cd} and the prompt, aliases, \texttt{;},
\texttt{\&} and \cmd{w}, an rc file, and commands from a pipe.
\item On the board, booted from a copy of the tether's disk with a
directory on the path, 44 checks the same way: among them a module on
the path that runs under its own name and is unlinked afterwards, a
procedure file on the path, \key{Ctrl/C} stopping a command that never
uses the terminal, \cmd{mfree} the same after running commands, and the
history kept across leaving and starting \cmd{tsh}. Booted from the
FujiNet, a shorter run. A command takes half a second from \key{Return}
to the next prompt, completing a command's name about one second, and a
file's name half a second.
\item Its first runs on the board found a fault in the firmware. A packet
to the tether with a run of exactly 254 bytes that are not zero, then a
zero, lost the zero: the COBS encoder took it for the end of a full
block, which has none. The history file, growing a line at a time, made
a sector like that, and the tether stopped at the short packet. Fixed in
\file{firmware/one/util/cobs.h}; the same sectors, copied on the board,
then came through whole.
\item CMOC made \texttt{err ? -1 : path}, with \texttt{path} a byte, a
byte expression: 255, not $-1$. So every failed open looked like path
255, until it was written as two statements.
\end{itemize}
